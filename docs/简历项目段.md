# 简历项目描述（2026-09-15 更新：n=3 完整消融 + 工具可靠性 / 缓存 / 记忆基准）

## 中文短版（简历 4–6 行）

**AI 旅行规划系统（Function Calling 多 Agent）**  
手写 OpenAI Function Calling 编排：**本地骨架 P95 1.1s 可见**（20 并发压测，对比同类 demo 白屏等 3–6 分钟）+ 3 层串并行 Agent 后台填充；Okapi BM25+FAISS 混合检索、GPS 路线 2-opt、PuLP 预算、SSE 断线回放与工具降级。内置 3 评委消融评测，**失败/降级 run 自动隔离不计分**；3 case 消融显示 multi 与 single **质量未见显著差异**（76.7 vs 80.0，分差小于波动 σ=5.8），但 single 快 1.6×、省 2.8×、三次结果零波动——**据此把产品默认档从 multi 切到 single**，用数据否决自己的架构设计；并实测出反思机制无质量收益却增加 30% 延迟。补全链路埋点：**本地工具成功率 95%**（最弱一环景点详情 80%，如实列出）、**缓存复用省 47.5% 外部调用**；故障注入验证容错链路（4 类故障救回 3 类）；用户记忆检索 MRR 0.812，超字面基线 60%。

## 中文详细版（网申/作品集）

- **问题 1（体验）**：多 Agent 一跑 3–6 分钟，用户面对白屏。
- **问题 2（价值）**：「Agent 多」不等于「方案更好」，需要量化而不是信仰。
- **做法**：
  1. progressive 骨架：知识库+路线 2-opt+LP 预算秒级拼出可读行程，SSE 先推骨架再由 Agent 填充；`skeleton_only` 模式支撑纯本地延迟基准；
  2. **延迟基准（可复现）**：`python -m eval.latency_bench`，20 请求 × 4 并发实测骨架事件 P50 803ms / **P95 1080ms**，TTFB P95 16ms；
  3. multi / sequential / single 可切换；拒绝工具调用伪正文；反思可关；
  4. 混合检索（FAISS + Okapi BM25，k1=1.5/b=0.75）+ GPS≤2.5km 邻近图谱；web_search 次数预算；
  5. 限流退避、工具 Fallback 链、SSE 事件持久化与 `after_id` 回放、LLM 全挂走本地离线降级；
  6. **评测器失败判定**：0 次 LLM 调用（降级）、评委解析失败、Agent 全失败的 run 自动隔离，失败明细单独列出——修复了旧版把 429 降级输出误计为 0 分「成功」的问题。

### 消融实测（3 case × 4 配置 / T001 东京 · T002 巴黎 · T003 曼谷 / mimo-v2.5-pro / 3 评委中位数）

| 配置 | 样本 | 平均分 | 波动σ | 平均耗时 | ~成本 |
|------|------|--------|--------|----------|-------|
| **single + 反思** | 3/3 | **80.0** | **±0.0** | **202s** | **$0.0097** |
| multi + 反思 | 3/3 | 76.7 | ±5.8 | 324s | $0.0275 |
| multi 无反思 | 3/3 | 76.7 | ±5.8 | 226s | $0.0349 |
| sequential + 反思 | 2/2 | 75.0 | ±7.1 | 471s | $0.0418 |

**三条结论：**

1. **multi vs single 分差 −3.3，但 σ=5.8（分差小于波动）** → 正确表述是「质量未见显著差异」。
   但质量相当的前提下 single 快 1.6×、省 2.8×、三次全部 80 分零波动，故默认档选 single。
   本质是**用数据否定了自己设计的多 Agent 架构**。
2. **反思机制未观测到质量收益**：开关反思得分完全一致（76.7，三个 case 逐个相同 70/80/80），
   关掉后反而快 30%。至少说明「反思没带来可观测的质量提升」。
3. **sequential 最差且最慢**（471s ≈ single 的 2.3×）→ 并行的价值在延迟，不在质量。

**为什么 multi 反而不占优（可深挖）**：multi 的 LLM 调用 16.7 次 vs single 6.3 次——多 Agent
各自调工具存在重复检索、Agent 间输出传递会压缩上下文丢失细节、且每个 Agent 独立触发
「输出无效→强制重写」放大 token 消耗。

**那多 Agent 的理由是什么（面试官 100% 会追问，必须答得上来）**：

先纠正口径——**数据没说 multi 不如 single**，只说「没观测到差异」。`single` 是 1 个 `planner_all`
Agent 拿全部 5 个工具、8 轮一把梭（`crew.py:1098` / `agents.py:141`）。它快是因为**只干 1/5 的活**
（6.3 次调用 vs 16.7 次），不是因为它更强。拿 single 的 202s 证明「多 Agent 没用」是逻辑错误。

多出来的 10 次调用买到的是**工程属性，不是分数**：

| 理由 | 证据强度 | 说法 |
|------|----------|------|
| **并行省墙钟** | ✅ 有硬数据 | sequential 471s → multi 324s，同为 5 Agent、同开反思，省 1.45× 且质量不掉（75.0 vs 76.7） |
| **上下文隔离** | ⚠️ 结构性（本次未验证） | single 要把 5 板块 + 全部工具返回塞进 1 个 context；任务越长越吃亏，3 case 短行程测不出来 |
| **失败隔离** | ✅ 结构性 | 一个 Agent 挂了其余 4 个照出内容；single 一把梭只能整体重来 |
| **可独立替换** | ✅ 结构性 | 改预算只需重跑 Budget Agent（内部是 PuLP 线性规划），single 只能整体重跑 |

**30 秒标准答法（背这个）**：

> 多 Agent 在这个项目里的价值不是分数，是工程属性——同等质量下并行省 1.45 倍墙钟、上下文隔离、
> 失败可局部重试、模块可独立替换。质量上我没测出差异（分差比波动还小），所以默认档选了更便宜的
> single，把 multi 留成可选的深挖档。这个结论是我跑消融跑出来的，不是抄来的。

**被追问「既然没提升，为什么不删掉 multi」**：

> 三个理由。第一，n=3 只够说「没观测到差异」，不够说「没有差异」，样本量不足以让我砍掉它。
> 第二，三档可切换的抽象——动态路由、分层调度、并行执行器——本身是工程量，也是我得出这个结论的
> 实验设施。第三，上下文隔离的收益理论上随任务变长而放大，3 case 的短行程测不出来，
> 这是我下一步要补的实验。**如果 n=10 复测 multi 依然没有质量差异，我会把它正式降级为实验档。**

> ⚠️ 加分点在于**你主动否定了自己的架构**。面试官见过太多「为了多 Agent 而多 Agent」的项目，
> 一个能拿出消融数据说「我测了，没收益，所以我换掉它」的候选人，比一个吹多 Agent 的候选人值钱。

### 可靠性与可观测性（离线可复现，不依赖 API 配额）

Agent 的可靠性不能只靠「跑通一次」证明，所以把重试/降级/缓存/记忆全部埋点并量化：

| 指标 | 实测 | 怎么测的 |
|------|------|----------|
| 本地工具成功率 | **95%**（76/80） | 10 城 × 4 工具 × 2 轮；景点详情最弱 80%，如实列出 |
| 最终可用率 / 一次成功率 | 75% / 25%（注入 4 类故障） | 区分二者才看得出工具本身稳不稳 |
| **容错依赖度** | 50% | 一半的调用靠重试或降级才成功 |
| 缓存命中率 | **47.5%**，省 38 次调用 | 同参数跑 2 轮；只缓存成功结果 |
| 记忆检索 MRR | **0.812 vs 基线 0.507（+60%）** | 12 条记忆 / 8 条措辞不重合的查询 |

`python -m eval.tool_bench` / `python -m eval.memory_bench` 一键复现；运行时指标 `GET /api/metrics/tools` 实时可查。

## 英文一行

Hand-rolled Function Calling travel multi-agent system (FastAPI) with skeleton-first streaming (**P95 ~1.1s** to a readable itinerary, 20-req benchmark), hybrid FAISS+Okapi BM25 retrieval, GPS 2-opt routing, LP budgeting, SSE replay, and ablation evals that quarantine degraded runs. A 3-case × 4-config ablation found no significant quality difference between multi and single agents (76.7 vs 80.0, gap smaller than σ=5.8), yet single was 1.6× faster and 2.8× cheaper with zero variance — so the product default is chosen by data, not by agent count; reflection was likewise shown to add 30% latency with no measurable quality gain.

## 口头自我介绍 20 秒

> 我做旅行规划 Agent，手写 Function Calling，不用框架。三个数字：骨架 1 秒内可见——用户不用白屏等几分钟；3 个 case 的消融里 multi 和 single 质量没有显著差异（分差比波动还小），但 multi 贵 2.8 倍、慢 1.6 倍，single 还更稳定——三次全是 80 分，所以我按数据把默认档切到 single；评测器会把降级和评委失败的样本隔离掉——宁可少样本，不要被污染的结论。

**被追问「你的 Agent 有多可靠」时接上**：

> 我给工具链路加了埋点。**真实负载下**：本地工具成功率 95%，最弱的是景点详情 80%。**故障注入下**（人为让工具失败，验证容错是否真的生效）：4 类故障里系统救回 3 类——重试救回一类、降级到备用工具救回一类，只有一类彻底失败。另外重复规划同一目的地时缓存能省掉 47.5% 的调用。用户记忆我做了离线评测，语义检索 MRR 0.812，字面匹配只有 0.507——这就是记忆系统值得做的证据。

**被追问「为什么不用多 Agent / 反思有用吗」时接上**：

> 反思这一项我专门做了消融：开和关的得分完全一样，都是 76.7，三个 case 逐个也一样，但关掉之后快 30%。所以我没把它当成质量手段，而是一个可选的成本项。多 Agent 同理——它在我这 3 个 case 上
不是质量的来源。**但并行的价值是被数据证明的**：同样的 5 个 Agent，串行 471s、并行 324s，省 1.45 倍墙钟
且质量没掉。所以我保留 multi 作为深度档，只是默认不给它。

> ⚠️ 分寸提醒：75% 可用率 / 25% 一次成功率是**注入故障的人造分布**，只用来证明容错链路确实生效，**绝不能当成真实系统的可靠性指标**对外讲。真实数字只有一个：本地工具成功率 95%。
>
> ⚠️ 另一处分寸：multi vs single 的 3.3 分差**小于** σ=5.8，所以只能说「未见显著差异」，**不能说「single 质量更好」**。但「质量相当 + 全面更优的成本和稳定性 → 所以选它」是完全站得住的。

## 使用注意

- 消融为 **n=3**（sequential 因跑批中断只有 n=2），属方向性结论；分差小于波动，不宣称显著差异。
- **不要把「未见显著差异」讲成「single 更优」**——面试官一问 σ 就会穿。
- 跑批期间外网不通，web_search 全部降级到本地知识库；各配置受影响一致，横向对比有效，但绝对分数偏低。
- Token/成本为字符粗估，仅横向对比。
- 延迟基准是纯本地链路（`skeleton_only`），不代表完整 Agent 耗时；两者在 README 分开呈现。
- **⚠️ 容错链路的 75% 可用率 / 25% 一次成功率 / 50% 容错依赖度，全部来自人为注入的 4 类故障**，只用于证明容错机制生效与防回归，**不能说成真实系统的可靠性**。真实可用的数字是「本地工具成功率 95%」。
- 工具成功率 95% 只覆盖本地工具；天气/汇率/网络搜索未计入（可用 `--include-network` 单独测）。
- 记忆评测用 12 条构造语料，证明的是「语义检索 vs 字面匹配」的相对优势，不是线上效果。
