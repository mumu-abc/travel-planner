# 简历项目描述（2026-09-14 更新：延迟基准 + 评测器修复后）

## 中文短版（简历 4–6 行）

**AI 旅行规划系统（Function Calling 多 Agent）**  
手写 OpenAI Function Calling 编排：**本地骨架 P95 1.1s 可见**（20 并发压测，对比同类 demo 白屏等 3–6 分钟）+ 3 层串并行 Agent 后台填充；Okapi BM25+FAISS 混合检索、GPS 路线 2-opt、PuLP 预算、SSE 断线回放与工具降级。内置 3 评委消融评测，**失败/降级 run 自动隔离不计分**；东京用例上 multi 与 single 同为 80 分但 multi 慢 1.8×/贵 2.3×——**据此把产品默认档从 multi 切到 single**，用数据否决自己的架构设计。

## 中文详细版（网申/作品集）

- **问题 1（体验）**：多 Agent 一跑 3–6 分钟，用户面对白屏。
- **问题 2（价值）**：「Agent 多」不等于「方案更好」，需要量化而不是信仰。
- **做法**：
  1. progressive 骨架：知识库+路线 2-opt+LP 预算秒级拼出可读行程，SSE 先推骨架再由 Agent 填充；`skeleton_only` 模式支撑纯本地延迟基准；
  2. **延迟基准（可复现）**：`python -m eval.latency_bench`，20 请求 × 4 并发实测骨架事件 P50 803ms / **P95 1080ms**，TTFB P95 16ms；
  3. multi / sequential / single 可切换；拒绝工具调用伪正文；反思可关；
  4. 混合检索（FAISS + Okapi BM25，k1=1.5/b=0.75）+ GPS≤2.5km 邻近图谱；web_search 次数预算；
  5. 限流退避、工具 Fallback 链、SSE 事件持久化与 `after_id` 回放、LLM 全挂走本地离线降级；
  6. **评测器失败判定**：0 次 LLM 调用（降级）、评委解析失败、Agent 全失败的 run 自动隔离，失败明细单独列出——修复了旧版把 429 降级输出误计为 0 分「成功」的问题。
- **实测（T001 东京 / mimo-v2.5-pro / 3 评委中位数，n=1 方向性结论）**：

| 配置 | 中位分 | 耗时 | ~成本 | 结论 |
|------|--------|------|-------|------|
| multi + 反思 | 80 | 378s | $0.022 | 质量与 single 打平 |
| single + 反思 | 80 | 215s | $0.010 | **更快更省 → 设为产品默认** |

- **结论**：该用例上 multi 未带来质量收益，却慢约 1.8 倍、贵约 2.3 倍。按数据把默认档切到 single，multi 保留为「要五板块齐全」的深度档；n≥3 复测后再定最终默认。

## 英文一行

Hand-rolled Function Calling travel multi-agent system (FastAPI) with skeleton-first streaming (**P95 ~1.1s** to a readable itinerary, 20-req benchmark), hybrid FAISS+Okapi BM25 retrieval, GPS 2-opt routing, LP budgeting, SSE replay, and ablation evals that quarantine degraded runs; multi matched single on quality (80/80) while costing ~2.3× more, so the product default is chosen by data, not by agent count.
