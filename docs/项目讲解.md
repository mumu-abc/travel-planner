# 项目讲解（面试用 · 按代码真实结构）

> 目标：被追问「这段为什么这么写」时能指到文件，而不是背 README。  
> 配套：`app/` 源码、`eval/report_ablation.md`、`docs/演示脚本.md`。

---

## 0. 一句话定位

**手写 OpenAI Function Calling 的旅行规划系统**：先本地骨架秒出，再多 Agent 填细节；同一套代码可跑 multi / sequential / single，用消融回答「多 Agent 值不值」。

---

## 1. 请求从进到出（主路径）

```
浏览器 index.html
  POST /api/plan/stream  {destination, days, budget, interests, mode, progressive}
        │
        ▼
app/routers/plan.py
  create_plan_pending → 若 progressive：app/skeleton.build_skeleton() → SSE skeleton
        │
        ▼
app/crew.build_travel_crew()
  注入偏好/反馈/记忆 → 选 Agent → 按 mode 切层 → 逐层执行
        │
        ▼
_run_agent_with_tools()
  FC 循环：LLM → tool_calls → _execute_tool_with_recovery → tool 消息回填
  → 伪正文检测/强制重写 → 可选自我反思
        │
        ▼
step_callback / token_callback / event_callback
  → Queue → SSE：agent_done / token / thought / action / observation / final
        │
        ▼
db.update_plan_result + 记忆提取
```

文件职责：

| 文件 | 干什么 |
|------|--------|
| `frontend/index.html` | 表单、SSE 消费、航线时间轴 UI |
| `app/routers/plan.py` | HTTP/SSE、骨架先推、followup/feedback |
| `app/skeleton.py` | 无 LLM 骨架：知识库+路线+LP |
| `app/agents.py` | Agent 定义、反思词、`split_layers` |
| `app/crew.py` | FC 引擎、模式执行、恢复、预算 |
| `app/tools/*` | 检索/路线/预算/天气/汇率/搜索 |
| `app/concurrency.py` | 令牌桶+退避 |
| `app/usage.py` | 粗计 token/成本 |
| `eval/eval_runner.py` | 多评委 + 消融 |

## 2. 三种执行模式（必考）

代码：`app/agents.py` + `build_travel_crew(mode=...)`

| mode | 层怎么切 | 何时用 |
|------|----------|--------|
| **multi** | L1 Researcher → L2 Planner → L3 Budget∥Foodie∥Safety | 要五板块齐全 |
| **sequential** | 五角色严格串行 | 消融：去掉并行 |
| **single** | 一个 `planner_all` | 消融 baseline / 默认性价比档 |

**共享上下文**：每完成一个 Agent，输出进 `context_parts`，下一层 user message = `base_request + 前序成果`。

**为何 L3 能并行**：Budget/Foodie/Safety 只读前两层结果，互不依赖；用 `ThreadPoolExecutor` + `parallel_stagger_sec` 错峰防 429。

## 3. Function Calling 循环（核心）

`_run_agent_with_tools`（约 `crew.py` 中部）：

1. messages = [system, user]  
2. 带 `tools=TOOLS` 调 chat.completions  
3. 无 `tool_calls` → 当成文结束  
4. 有 `tool_calls` → `_process_tool_calls` 执行并 `role=tool` 回填  
5. 最多 `max_tool_rounds`（默认 3；`planner_all` 用 8）  
6. 轮次耗尽 → `_stream_final_output`（**不带 tools**，强制成文）

**工具失败** `_execute_tool_with_recovery`：

- 重试 1 次  
- 查 `_TOOL_FALLBACKS`（如 search_knowledge → web_search）  
- 全失败 → 文案让模型写「暂无数据」

**成本预算**：`web_search` 超 `MAX_WEB_SEARCH_CALLS` 自动改 `search_knowledge`。

**伪正文（坑）**：模型有时把 `<tool_call>` 当最终答案。  
逻辑在 `crew.py` `_ensure_valid_final_output`（由原 ~863 内联块抽出）：
1. `_is_valid_plan_text`：非伪工具且 ≥120 字  
2. 否则有 tools 对话上强制重写（≥80 且非伪）  
3. 仍失败 → 无 tools 再生成（`token_callback=None`，避免脏流先到前端）  
4. 再失败 → 明确错误串  
（曾导致 single 评测 20 分，修复后 70+。）

## 3.5 为什么不用 LangChain（高频必问）

> ⚠️ 这题问的不只是技术，是在试探你**主动选的**还是**不会用所以不用**。
> 所以第一句必须先承认框架有价值，再讲自己为什么不需要。

### 30 秒标准答法（背这段）

> "不是排斥框架——我项目里其实装了 **LangSmith** 做 tracing。
> 主要是**我的链路短、要控的东西碎**，自己写更划算。
> 比如模型调工具**经常漏参数**，查知识库忘了传目的地，我就在工具层做兜底，
> 自动把当前城市补进去；还有一种更阴的——思维链模型额度被推理链吃满，
> 正文直接返回空，我得看 `finish_reason` 分辨是正常结束还是被截断，再决定要不要重试。
> 框架会在中间加一层抽象，模型返回的怪东西可能被它抹平，出问题很难定位是哪层。
> 我这个循环就几十行，全在明面上。"

### 为什么这么讲

| 要点 | 作用 |
|------|------|
| 先提 LangSmith | 证明"不是排斥生态"，有事实支撑（requirements.txt 里真有） |
| 讲**具体踩坑**不讲话术 | 说"参数归一化"是行话没人懂；说"漏传目的地我兜底"谁都懂 |
| "抽象层会抹平怪返回" | 这是**框架的真实代价**，说出来显得你懂框架而不只是躲它 |
| "我的循环几十行" | 把"自己写"从"重复造轮子"翻转成"链路本来就短" |

### 两个例子在代码里的位置（被追问就指）

- 漏参数兜底 → `crew.py` `_normalize_tool_args()`：工具参数缺 `destination` 时，
  用当前规划的目的地补上（注释里写明"不逼 LLM 编城市名"）。
- `finish_reason` 判空 → `crew.py` `_run_agent_with_tools()` 内：
  模型既没给工具调用也没给正文时（实测 `finish_reason=tool_calls`），
  不能当成"答完了"，要降级重试一次。

### 追问预案

**Q：那你不就是在重复造轮子？**
> "功能上有重叠。但我这个规模，框架带来的收益小于它带来的调试成本。
> 而且我**保留了迁移路径**——工具定义是标准 OpenAI 格式，哪天要换框架，迁移成本很低。"

**Q：LangChain 能做的事你都能做？**
> "不敢这么说。它的生态、预制工具、多模型适配我没实现。
> 我实现的只是**我这个场景需要的那部分**：工具循环、失败恢复、参数兜底、流式输出。
> 换个需要大量现成集成器的场景，我会直接用框架。"

**Q：如果重来一次还会手写吗？**
> "看规模。链路这么短我还会手写；
> 如果要接十几个数据源、还是要接不同厂商模型，我会用框架。"

### 分寸提醒 ⚠️

- ❌ 不要说"LangChain 太重/太烂/不好用"——得罪人且显得偏激。
- ❌ 不要只说"轻量、好调试"——这是所有人都会说的便宜话，没证据。
- ✅ 承认框架解决的问题，说清你的场景不需要它。
- ✅ 一定要给**具体例子**，这是把"我懒"和"我权衡过"区分开的唯一东西。

## 4. 骨架优先（用户体感）

`app/skeleton.py`：不调 LLM。

1. 匹配 `DESTINATIONS`  
2. `optimize_route_from_knowledge`（GPS + 2-opt）  
3. `optimize_budget`（PuLP）  
4. 拼 Markdown → SSE `skeleton`  
5. Agent 跑完 `final` **整体替换**

前端徽章：骨架预览（琥珀）→ 生成中（青）→ 完成（绿）。

## 5. 检索与算法工具

### 混合检索 `app/tools/knowledge_search.py`

- FAISS：`bge-small-zh-v1.5` + IP  
- BM25：**查询期** Okapi，k1=1.5，b=0.75（不是建索引时写死分）  
- 融合：0.7 语义 + 0.3 关键词  
- 图谱：`ATTRACTION_COORDS` 真 GPS，Haversine ≤2.5km 排序，返回 `nearby_km`

### 路线 `route_optimizer.py`

贪心最近邻 + 2-opt；测试保证 2-opt 不劣于贪心。

### 预算 `budget_optimizer.py`

PuLP 约束分配；不可用回退比例。

## 7. 评测与真实数字（以 `eval/report_ablation.md` 2026-09-15 为准）

`eval/eval_runner.py --ablation`：同一批 case 跑 multi / single / sequential / 关反思。

**n=3（T001 东京 / T002 巴黎 / T003 曼谷）：**

| 配置 | 成功 | 平均分 | 耗时 | ~成本 | LLM次 |
|------|------|--------|------|-------|-------|
| **single + 反思** | 3/3 | **80.0** | **202s** | **$0.010** | 6.3 |
| multi + 反思 | 3/3 | 76.7 | 324s | $0.028 | 16.7 |
| multi 关反思 | 3/3 | 76.7 | 226s | $0.035 | 17.3 |
| sequential | 2/2 | 75.0 | 471s | $0.042 | 21.5 |

**结论（情况 B）：**
- multi 与 single **质量未见显著差异**（分差 −3.3 < 波动 σ=5.8）
- single 快约 **1.6×**、省约 **2.8×**，且 σ=0 更稳
- 反思在本测试**无质量收益，只加延迟**
- **产品默认 single**，multi 作深度档——用数据否定「Agent 越多越好」

面试口径：  
「消融是为了定产品默认，不是为了证明 multi 必胜。」

## 9. 高频追问速答

**为什么不用 LangChain？**  
见 **§3.5**（完整版）。速答版：
> "不是排斥框架——我装了 LangSmith 做 tracing。
> 主要是我链路短、要控的东西碎：模型调工具**漏传目的地**要兜底、
> **思维链吃满额度导致正文为空**要看 `finish_reason` 分辨。
> 框架的抽象层可能把这些怪返回抹平，出问题难定位。我自己那个循环几十行，全在明面上。"
>
> ⚠️ 别说"LangChain 太重/太烂"；说"轻量好 debug"没证据，要给具体例子。

**Router 一定跑吗？**  
仅 multi 且 `enable_routing`；失败退关键词路由；single/sequential 不路由。

**反思为什么可关？**  
每次最多多 1–2 次 LLM；演示/评测用关反思换延迟。

**和「课设模板」区别？**  
有消融、骨架、成本预算、伪正文治理、诚实报告失败；不是只堆 5 个角色。

**最大诚实边界？**  
28 城静态知识库；LLM-as-judge 有偏；单机 SQLite；multi 未在所有 case 显著更优。

## 10. 30 秒电梯稿

> 这是手写 Function Calling 的旅行规划系统。用户点生成后先出本地骨架，再由多 Agent 填细节。系统支持 multi/sequential/single，我用同一套评委回答多 Agent 值不值——结论按数字定默认路径。工程上有限流退避、工具降级、SSE 断线回放；前端把 Agent 做成航线时间轴，演示时能指着讲清依赖和并行。
