# Part 0 · 30 秒开场（必背，一字不差）

## 一句话定位

> 一个**手写 Function Calling** 的多 Agent 旅行规划系统（FastAPI）。
> 核心不是「多 Agent」，而是**用消融实验量化多 Agent 到底值不值**——
> 结论是质量打平但更慢更贵，所以**默认档改成了单 Agent**。

**为什么这句话有杀伤力**：大部分候选人说「我做了个多 Agent 系统」，
你说「我做了个多 Agent 系统，然后用数据证明它在这个场景下不划算」。
后者是工程师，前者是调库侠。

**项目真正在回答的两个问题**：
1. 体感：多 Agent 一跑几分钟，用户等不了 → 骨架优先压进 1 秒
2. 价值：多 Agent 相比单 Agent，质量/延迟/成本差多少 → 消融评测

## 三条结论（决定你是不是会思考的人）

1. **multi vs single 分差 −3.3，但 σ=5.8 → 分差小于波动**
   → 正确表述是「**质量未见显著差异**」，**不能说 single 更好**。
   质量相当时 single 快 1.6×、省 2.8×、三次全 80 分零波动 → 默认选 single。
   **本质：用数据否定了自己设计的多 Agent 架构。**

2. **反思机制未观测到质量收益**
   → 开关反思得分完全一致（76.7，三个 case 逐个相同），关掉反而快 30%。
   n=3 存在巧合可能，但足以说明「没有可观测提升」。

3. **sequential 最差且最慢**（471s = single 的 2.3×）
   → **并行的价值在延迟，不在质量**。

## 被追问「那还要多 Agent 干嘛」→ 30 秒标准答法（必背）

> ⚠️ 这是本题的**送命题**。你说完「我用数据否定了多 Agent」，面试官 100% 会接这句。
> 答不上来 = 前面的亮点全部作废；答好了 = 全场最高光。完整版见 **P24**。

> 多 Agent 在这个项目里的价值不是分数，是**工程属性**——同等质量下并行省 1.45 倍墙钟、
> 上下文隔离、失败可局部重试、模块可独立替换。质量上我没测出差异（分差比波动还小），
> 所以默认档选了更便宜的 single，把 multi 留成可选的深挖档。
> **这个结论是我跑消融跑出来的，不是抄来的。**

**一句话记住对照组**：证明"并行有用"要拿 **sequential（471s）比 multi（324s）**，
**不能**拿 single（202s）比——single 快是因为它只有 1 个 Agent、只干 1/5 的活。

# Part 1 · 项目理解速查

> 项目是 AI 生成的记不住？**因为你没参与决策**。
> 人脑记的是「我为什么选 A 不选 B」，不是「第 38 行写了什么」。
> 所以不要通读代码——先看数据流，再对每个模块问「**代价是什么**」。

## 1.1 数据流：一次请求走完全程

```
POST /api/plan/stream            app/routers/plan.py:89
  │
  ├─ 建 pending 记录（拿到 plan_id）         plan.py:94
  │
  ├─【骨架优先】不调 LLM，本地拼可读行程      plan.py:97 → app/skeleton.py:29
  │    知识库 + GPS 路线优化 + LP 预算
  │    推 SSE 事件 type=skeleton（P50 803ms）
  │    同时落库 db.save_sse_event ← 为断线重连
  │
  └─ build_travel_crew(...)                  app/crew.py:988
        │
        ├─ 注入用户历史偏好（user_preferences 表）   crew.py:1040
        ├─ 注入历史反馈闭环（低分→警告，高分→强化） crew.py:1058
        ├─ 注入语义记忆（FAISS 检索 top5）          crew.py:1083
        │
        ├─【路由】LLM 决定调哪几个 Agent            crew.py:909
        │     失败降级为关键词规则路由               crew.py:963
        │
        ├─【分层执行】split_layers()                app/agents.py:236
        │     L1 researcher → L2 planner → L3{budget,foodie,safety} 并行
        │     层内 ThreadPoolExecutor(4) + 错峰 1.5s 降 429
        │     前序输出拼成上下文给后序
        │
        └─【每个 Agent 内部】_run_agent_with_tools  crew.py:797
              Thought → Action(工具) → Observation → 循环(≤3轮)
                          │
                          └─ 失败：重试1次 → fallback链 → 降级文案
              → 输出校验（拒收工具调用伪文本）
              → 自我反思（PASS 则过，否则修正一次）
```

**关键细节（追问点）**
- 骨架和 Agent 是**两条独立路径**，骨架不调 LLM，断网也能出东西
- SSE 事件**落 SQLite**，断线用 `GET /api/plan/{id}/events?after_id=` 回放；`token` 不落库（量太大）
- 上下文传递是**纯字符串拼接**（`━━━ 前序 Agent 的工作成果 ━━━`），不是共享内存
- `mode=single` 时跳过路由与分层，一个 `planner_all` 直接出全文（工具轮次提到 8 轮）

## 1.2 模块地图

| 文件 | 职责 | 面试怎么讲 |
|------|------|-----------|
| `app/agents.py` | 5 Agent 定义 + 反思 prompt + 分层 | 拆出来自 crew 是为了**可单测、可做消融** |
| `app/crew.py` | FC 引擎 · 路由 · 工具恢复 · 成本预算 | 中枢，最该熟的文件 |
| `app/skeleton.py` | 本地骨架生成（无 LLM） | 体感优化核心，803ms 的来源 |
| `app/concurrency.py` | 令牌桶 + 信号量 + 指数退避 | 10 RPS / 并发 5 / 退避带 ±20% 抖动 |
| `app/tools/knowledge_search.py` | FAISS + Okapi BM25 + GPS 图谱 | 混合检索，融合 0.7/0.3 |
| `app/tools/route_optimizer.py` | Haversine + 贪心最近邻 + 2-opt | 测试保证 2-opt 不差于贪心 |
| `app/tools/budget_optimizer.py` | PuLP 线性规划 | LP 不可用时回退比例分配 |
| `app/memory.py` | 偏好 + 向量记忆 | Recall@3 87.5%，MRR 比基线 +60% |
| `app/tool_metrics.py` | 工具成功率/降级率埋点 | **旁路记录，异常不影响主流程** |
| `app/tool_cache.py` | TTL 缓存，只缓存成功结果 | 失败不入库，避免固化瞬时故障 |
| `app/routers/plan.py` | SSE + 多轮 + 反馈 + 记忆 API | 多轮超 10 条做历史摘要 |
| `eval/eval_runner.py` | 消融评测 CLI | 有 `--check-quota`，429 时直接退出 |

## 1.3 设计决策与 trade-off（每个都要能说代价）

| 决策 | 为什么 | 代价 / 边界 |
|------|--------|------------|
| 默认 `single` 而非 `multi` | 消融：质量打平，快 1.6× 省 2.8× | 五板块齐全度不如 multi，故保留 multi 为深度档 |
| 骨架优先 | 3–6 分钟白屏不可接受 | 骨架是静态知识库，可能与最终方案有出入 |
| 手写 FC 不用 LangChain | 依赖轻、可控、无黑盒 | 自己实现循环/解析/容错，代码量大 |
| 混合检索 0.7/0.3 | 语义召回泛化 + BM25 保专有名词 | 权重是拍的，没做网格搜索 |
| 自建 BM25 | k1/b 可解释，中文按字切分 | 中文按字不如 jieba 分词准 |
| GPS 邻近图（≤2.5km） | 真距离，不是「列表相邻冒充图谱」 | 只有部分景点有坐标（`has_gps` 标了） |
| 工具 TTL 缓存 | 同城重复查询复用 | **只缓存成功结果**；天气 30min/汇率 1h/静态 24h |
| web_search 限次（2 次） | 贵工具不能想调就调 | 超预算自动降级本地知识库 |
| 反思可关 | 每次最多多 2 次 LLM 调用 | 消融显示无质量收益 → 演示可关 |
| 埋点旁路化 | 观测不能拖垮主流程 | 整体 try/except 兜底 |

31. **多 Agent 质量没提升，那它的价值是什么？**（→ P24）
    必答到：并行省 1.45× 墙钟（有数据）+ 上下文隔离 / 失败隔离 / 可独立替换（结构性，未验证）。
32. **证明「并行有用」该拿哪两个配置比？**（→ P24）
    答：**sequential 471s vs multi 324s**。
    **不能**拿 single 202s 比——single 只有 1 个 Agent、6.3 次调用，是活少了不是变强了。
33. **查一个知识库里没有的城市，会发生什么？**（→ P25）
    答：**不会说"没有"，会返回语义最接近的 k 条**——查「梅州五华」返回吉隆坡 / 孟买 / 阿根廷。
    这是**检索静默失败**，不是幻觉：内容全是真的，只是跟查询无关，所以更难发现。
34. **为什么不直接用分数阈值把不相关的滤掉？**（→ P25）
    答：实测不相关最高分 **0.56**、相关最高分 **0.68**，**只差 0.12**，阈值标定不住会误伤。
    改用**确定性判据**：目的地归属 / 覆盖校验，不需要标定。
35. **联网搜索在国内能用吗？实测多少？**（→ P26）
    答：**不能**。DuckDuckGo 20.7s / 中文维基 9.8s，`web_search` 合计 **28.3 秒 / 0 条**。
    换**必应中国 RSS** 后 **0.33 秒 / 3 条中文结果**。
36. **为什么不干脆只换引擎，还要加冷却短路？**（→ P26）
    答：换引擎解决「搜不到」，冷却短路解决「搜不到时别拖垮流水线」。
    必应 RSS 是未公开接口，一定会坏 —— 我要的是它**坏得体面**（连续失败 2 次 → 冷却 5 分钟直接跳过）。
    **一个 28 秒才返回的兜底，比没有兜底更糟。**

## 1.6 已知边界（被问「有什么不足」时照实说）

主动承认比被戳穿强一百倍：

- 消融 n=3（sequential n=2），**方向性结论**，分差 < 波动，不宣称 single 更好
- 工具成功率 95% **只覆盖本地工具**，天气/汇率/搜索走外部 API 未计入
- 缓存命中率 47.5% 来自合成负载，真实重复率取决于用户行为
- 记忆评测用**构造语料**，证明的是方法相对优势，不是线上效果
- 容错 4 类故障是**注入**的，不代表真实故障分布
- 单机 SQLite、无鉴权、无多租户 —— 是工程作品不是 SaaS
- 评委是 LLM-as-judge，有偏差，正式应加人工抽检
- **没做 rerank**（见 S4，这是最常被问到的短板）
- **输出质检用固定长度阈值，没检查 `finish_reason`**（2026-09-16 定位）：
  判定「最终输出无效」用的是「像工具调用文本 或 长度 < 120 字」，**没有看模型是不是被 `max_tokens` 截断**。
  推理模型的 thinking 会占输出预算，正文被截短时会被误判成"写太短"→ 强制重写一次（整段 messages 重发）。

# Part 2 · 八股题 B1–B21（答案版）

## 一、Agent 通用概念（8题）

### ★★★ B1. 工作流和 Agent 的区别？

**核心区别在于「确定性」和「自主性」。**

| 维度 | 工作流（Workflow） | Agent |
|------|-------------------|-------|
| **执行路径** | 固定/预定义，按步骤走 | 动态/自主，LLM 决定下一步做什么 |
| **决策主体** | 代码逻辑（条件分支、循环） | LLM（推理-行动循环） |
| **适用场景** | 流程固定、规则明确 | 需要探索、推理、判断 |
| **可预测性** | 高，输入→输出映射确定 | 低，同一输入可能不同路径 |
| **状态管理** | 显式状态变量 | 隐式（对话历史 + 工具结果） |
| **调试难度** | 低，打日志就能追踪 | 高，需要 tracing 工具 |

**一句话**：工作流是「铁轨」，轨道铺好火车按路线跑；Agent 是「自动驾驶汽车」，自己决定走哪条路、在哪停。

**实践中的组合**：成熟系统通常不是二选一，而是「**工作流管外层流程（保证可预测），Agent 管内层推理（保证灵活性）**」。
本项目中外层 3 层执行计划是工作流，内层每个 Agent 用 Function Calling ReAct 循环。

---

### ★★ B2. Skill 和工具的区别？

**从抽象层次和复杂度区分。**

| 维度 | 工具（Tool） | Skill（技能） |
|------|-------------|--------------|
| **抽象层次** | 原子能力，单一函数 | 复合能力，可能含多个工具+推理 |
| **复杂度** | 低：输入→处理→输出 | 高：可能多步推理、多次工具调用 |
| **调用方式** | 直接函数调用 / tool calling | 由 Agent 自主编排使用 |
| **状态** | 无状态（或外部状态） | 可以有内部状态和记忆 |
| **类比** | 单个工具（锤子、螺丝刀） | 完整技能（木工、修车） |

**一句话**：工具是「一个函数调用」，Skill 是「能独立完成一类任务的能力单元」。工具是 Skill 的组成部分。

---

### ★★★ B3. Agent 优化常见手段？

**9 个方向：**

1. **Prompt 优化**：Few-shot 示例、思维链（CoT）、角色设定、输出格式约束
2. **结构化输出**：Pydantic schema / JSON mode 强约束，比纯文本可靠
3. **工具工程**：工具描述清晰、参数类型明确、粒度适中
4. **记忆增强**：短期（对话上下文）+ 长期（向量检索）+ 实体记忆
5. **RAG 优化**：分块策略、检索重排序、多轮检索、HyDE
6. **流程优化**：单轮改 ReAct 循环、串行改并行、增加自检
7. **容错机制**：重试、降级、兜底、超时控制、异常捕获
8. **评测驱动**：建评测集，量化优化效果，防回归
9. **反馈闭环**：用户反馈 → 归因 → 调整 → 再评测

**优先级**：先做结构化输出（立竿见影）→ 再建评测体系（知道改没改好）→ 然后记忆增强和流程优化 → 最后反馈闭环。

---

### ★★★ B4. 怎么让模型规范调用工具，不瞎编参数？

**四层保障，从强到弱：**

**第一层：类型注解 schema 强约束（最有效）**
工具参数用 JSON Schema 定义，框架自动把 schema 传给模型。模型输出的 tool call 会被校验，不符合直接报错重试。

**第二层：结构化输出约束**
需要结构化输出时指定 `response_format` 或 JSON mode。

**第三层：系统提示词明确约束**
写明有哪些工具、每个工具的作用和参数要求、什么时候该调、不知道就说不知道。

**第四层：ReAct 循环 + 观测反馈**
ReAct 本身有纠错机制——工具返回「未找到信息」，模型看到 observation 后会修正，换个查询再试。

---

### ★★ B5. 参数缺失场景怎么解决？

**五步处理法：**

1. **默认值兜底**：Pydantic 字段设默认值，解析不出来就用默认，流程不中断
2. **尽力解析**：LLM 从自然语言里尽可能挖信息
3. **保守策略假设**：关键参数缺失用保守值（未提供天数默认 3 天、预算默认 $2000）
4. **报告提示确认**：标注「信息不完整」，把判断权还给决策者
5. **多轮补全（进阶）**：检测到关键信息缺失，主动追问用户

**本项目实现**：`_normalize_tool_args()`（`crew.py:403`）自动适配参数名错误——
`search_knowledge` 缺 `query` 时用 `destination`/`category`/`raw` 代替，
`get_exchange_rate` 缺 `amount_usd` 默认 1000。

---

### ★★★ B6. 模型输出结果如何控制？

**五层控制，从强到弱：**

1. **JSON Schema 强约束（最强）**：约束参数类型和必填字段
2. **后处理归一化**：LLM 输出非标准值时，用映射字典做后处理
3. **系统提示词规则**：明确输出规则、格式要求、必须包含的章节
4. **后处理校验**：输出后再做一轮代码校验（字段完整、格式正确）
5. **自我反思机制**：反思 prompt 检查输出是否满足要求，不通过自动修正

**本项目额外一层**：`_looks_like_tool_dump()` 拒收「伪正文」——
模型把 `<tool_call>` / JSON 当最终答案吐出时强制重写（修这个 bug 让某配置从 20 分→70+）。

---

### ★★★ B7. 工具调用失败超时怎么处理？

**四层容错，从预防到兜底：**

**第一层：前置预防**
- 超时控制：LLM 调用设 timeout，防无限等待
- 重试：max_retries，指数退避 + 抖动，处理 429/503/timeout
- 参数校验：调用前先归一化参数

**第二层：调用时容错**
- try/except 包裹，失败不崩溃
- 降级返回：返回结构化错误信息，让 LLM 知道调用失败了
- ReAct 循环自然重试：模型看到错误可能修正参数再试

**第三层：Fallback 工具链**
失败后自动尝试替代工具（`search_knowledge` 失败 → `web_search`）。

**第四层：全局降级**
所有 Agent 都失败时，用本地工具生成基础方案（不调 LLM，只靠知识库+算法）。

---

### ★★★ B8. 容错异常机制怎么设计？

**四道防线 + 两种运行模式 + 配套基础设施。**

**四道防线（由内向外）：**

1. **工具/函数层**：工具函数加 try-except，不直接抛异常，把错误封装成结构化信息返回给 Agent 作为 Observation，让模型感知错误。失败后自动尝试 fallback 工具。
2. **Agent 业务层**：处理 LLM 输出解析异常；参数归一化兜底；自我反思不通过自动修正；重试耗尽后提供兜底结果，避免中断。
3. **工作流编排层**：3 层执行计划中单 Agent 失败不影响其他 Agent；失败标记为「生成失败」但不中断整体流程。
4. **对外 API 层**：最外层统一捕获异常，返回标准化错误格式，原始堆栈不对外暴露。

**两种容错模式：**
- **宽松模式**：单 Agent 失败允许降级继续，结果标注不完整。适合旅行规划——宁可少一个板块也要出方案。
- **严格模式**：关键节点失败直接终止报错。适合高危业务。

**配套基础设施：** 完整异常堆栈日志 · LangSmith 全链路 Tracing · 超时+指数退避+令牌桶限流 · SSE 事件持久化支持断线重连。

## 二、评测与调试（4题）

### ★★★ B9. Badcase 怎么定位环节？提示词还是微调？

**「逐层排查、归因分类」，然后决定怎么修。**

**定位流程（从下往上查）：**
1. **看输入**：需求理解对不对？参数提取对不对？
2. **看数据层**：知识库有没有这个数据？工具返回了什么？
3. **看推理层**：ReAct 过程中工具调用对不对？推理逻辑有问题吗？
4. **看输出层**：格式对不对？结构完整吗？

**归因分类：**
- **缺失归因**（该有的没有）→ 走「补」的路径：补数据、补工具、补 prompt 示例
- **错误归因**（不该有的有了）→ 走「修」的路径：调 prompt、加约束、加校验

**提示词 vs 微调？**
- **优先调 prompt**：90% 的 Badcase 都能通过优化 prompt 解决
- **微调什么时候用**：prompt 优化到顶了还有系统性偏差才考虑
- **记住**：用微调「记住知识」是错的，知识该走 RAG

### ★★★ B10. 修好一类坏一类怎么解决？

**这是「回归问题」，核心解法是「评测兜底 + 渐进式优化」。**

1. **回归检测**：每次改动后跑完整评测集，分数下降超阈值就告警
2. **分场景指标监控**：按维度（完整性/实用性/结构化）拆开看，某个维度掉了一眼发现
3. **A/B 对比**：大改动不直接替换，新旧版本并行跑，对比各维度分数

### ★★ B11. 没有用户反馈怎么抽检？

**三种方法：**

1. **LLM-as-Judge 自动抽检**：多个 LLM 当裁判，按不同维度（完整性/实用性/结构化）并行打分，取中位数
2. **黄金数据集回归抽检**：维护标注测试集，每次发布前跑一遍，关键指标不能下降
3. **分层抽样人工审核**：按目的地、预算等级分层抽样，人工审核高风险场景

### ★★★ B12. 长对话 token 消耗如何减少？

1. **对话历史摘要**：超 10 轮时，用 LLM 把早期对话压缩成 200 字摘要，只保留最近 4 条原文
2. **工具结果截断**：工具返回只取前 300 字符拼入 Observation，不传全文
3. **记忆检索 top-k 限制**：向量记忆只检索 top-5，避免上下文膨胀
4. **规划文本截断**：传给评委的规划文本截断到前 4000 字符
5. **Agent 间传摘要不传全文**：Layer 间共享的是前序 Agent 的成果文本，不是完整消息历史

### ★★★ B14. Agent 怎么调用工具？

**OpenAI Function Calling 机制，完整流程：**

1. 工具定义 → JSON Schema 格式的 function 定义
2. LLM 推理 → 模型根据任务和工具描述决定调哪个工具、传什么参数
3. 工具调用解析 → 从 `tool_calls` 字段提取函数名+参数
4. 执行工具 → 调用实际 Python 函数，拿到返回结果
5. 结果回传 → 把结果作为 tool message 拼入消息历史
6. LLM 再推理 → 看到结果后决定继续调工具还是输出最终答案
7. 循环直到无 tool_calls → 输出最终结论

**关键**：模型不执行函数，只输出调用意图；执行在你自己的进程里。

### ★★★ B15. 为什么选 OpenAI Function Calling 不选 LangChain？

**选 Function Calling 直接调用，三个原因：**

1. **完全控制**：工具调用的每一步都自己控制——参数归一化、错误恢复、Fallback 链、自我反思，都可定制。LangChain 的 `create_react_agent` 封装太重，加自定义逻辑要 hack 框架。
2. **依赖少**：不需要 LangChain 生态（LangSmith、LangGraph），生产部署更轻量。
3. **调试直观**：直接看 API 请求/响应，打日志就能追踪。

**LangSmith 仍然用了**：做可观测性（`@traceable` + `wrap_openai`），但只是**观测层**，不依赖它做流程控制。未配置时降级为 no-op。

### ★★★ B16. 怎么做可观测性？

**LangSmith tracing + 自定义 AgentTrace 双管齐下。**

**LangSmith tracing：**

- `wrap_openai()` 包装 OpenAI 客户端，自动追踪所有 LLM 调用

### ★★ B19. 删重复字符，字典序最小，相对位置不变

**题目**：给定字符串 s，删除重复字符使每个字符只出现一次，结果字典序最小。

**思路：单调栈 + 贪心**

```python
def removeDuplicateLetters(s: str) -> str:
    stack = []
    in_stack = set()
    last_occur = {}

    for i, c in enumerate(s):
        last_occur[c] = i

    for i, c in enumerate(s):
        if c in in_stack:
            continue
        while stack and stack[-1] > c and last_occur[stack[-1]] > i:
            removed = stack.pop()
            in_stack.remove(removed)
        stack.append(c)
        in_stack.add(c)

    return ''.join(stack)
```

**复杂度**：时间 O(n)，空间 O(26) = O(1)

**思路：贪心 + 回溯**

从高位到低位逐位确定：优先尝试放和 n 对应位相等的数字，不可行则找比 n 对应位小的最大数字，后面全放最大的数字。

### ★★ B21. 爬楼梯方法数 + 空间优化

**题目**：爬楼梯，每次爬 1 或 2 阶，爬到第 n 阶有多少种方法？空间 O(1)。

```python
def climbStairs(n: int) -> int:
    if n <= 2:
        return n
    prev2 = 1
    prev1 = 2
    for i in range(3, n + 1):
        curr = prev1 + prev2
        prev2 = prev1
        prev1 = curr
    return prev1
```

**复杂度**：时间 O(n)，空间 O(1)

### ★★★ P1. 框架：ReAct 还是 Plan-and-Execute？

**我用的是 ReAct + 3 层执行计划的混合架构。**

5 个 Agent（Researcher、Planner、Budget、Foodie、Safety）每个都用 OpenAI Function Calling 实现 ReAct 循环——LLM 自主决定调什么工具、调几轮，Thought → Action → Observation 交替。这适合需要灵活探索的场景。

但整体流程层面是 Plan-and-Execute 的 3 层执行计划：
- Layer 1: Researcher（信息收集）
- Layer 2: Planner（行程规划，共享 Researcher 成果）
- Layer 3（并行）: Budget + Foodie + Safety（共享 Researcher + Planner 成果）

**为什么不选纯 Plan-and-Execute？** 旅行规划中工具调用不需要复杂规划——查天气就是查天气，ReAct 的自主循环足够了。反倒是整体流程的层级依赖更重要（Planner 依赖 Researcher 的成果），所以用 3 层执行计划做外层编排。

**一句话**：工作流管外层（确定依赖），Agent 管内层（灵活探索）。

---

### ★★★ P2. 架构选型：直接调 API 还是用框架？串行还是并行？

**直接调 OpenAI API，不用 LangChain/LangGraph。3 层串并行混合执行。**

**为什么不用框架？**
1. **完全控制**：参数归一化、错误恢复 Fallback 链、自我反思，都可定制
2. **依赖少**：不需要 LangChain 整个生态，生产部署更轻量
3. **调试直观**：直接看 API 请求/响应，打日志就能追踪

**串行还是并行？**
```
Layer 1: Researcher（串行，先执行）
    ↓ 共享成果
Layer 2: Planner（串行，等 Layer 1 完成）
    ↓ 共享成果
Layer 3: Budget + Foodie + Safety（并行，ThreadPoolExecutor）
```

**为什么不全并行？** Planner 依赖 Researcher 的调研结果才能规划行程，Budget/Foodie/Safety 依赖 Planner 的行程安排。有依赖关系就不能全并行。

**为什么 Layer 3 能并行？** 三个 Agent 互不依赖，都只读前两层成果。用 `ThreadPoolExecutor` + 错峰启动避免 429。

**并用数据验证了**：`sequential` 模式五角色严格串行，消融实测 471s，是 single 的 2.3×——**并行的价值在延迟，不在质量**。

### ★★★ P3. 单/多 Agent？各子 Agent 分工？ `[已修正：默认档]`

**答：系统内置三种可切换模式，用消融证明「多 Agent 是否值得」；实测质量打平但更慢更贵，所以产品默认单 Agent。**

| 模式 | 含义 | 用途 |
|------|------|------|
| `single` | 单个 `planner_all` 写完 5 板块 | **产品默认**（`config.py:40`） |
| `multi` | Router + 3 层串并行 | 深度档：要五板块齐全时用 |
| `sequential` | 5 个专项 Agent 严格串行 | 消融：去掉并行 |

> 且注释写明「按消融数据选性价比档；multi 保留为『五板块齐全』深度档」。

**多 Agent 模式下的分工：**

| Agent | 功能 | 层级 | 主要工具 |
|-------|------|------|---------|
| Router | 意图分析，动态路由 | 0 | 0（纯 LLM 推理） |

| Planner | 行程规划 | 2 | 路线优化/景点详情/知识库 |

**设计思路**：每个 Agent 职责单一；Researcher 是基础 Agent，Planner 依赖其成果，Layer 3 互不依赖可并行。multi 下 `researcher` 和 `safety` 被强制包含。

**这是本题的题眼**：多 Agent 不是信仰，是可测量的取舍。我的消融显示 multi 相对 single 分差 −3.3 但 σ=5.8（分差小于波动），质量未见显著差异，而 single 快 1.6×、省 2.8×——所以我默认选了 single，把自己设计的多 Agent 架构降级成了可选深度档。

### ★★★ P4. 多智能体怎么协作？共享上下文怎么传？

**协作模式是「3 层串并行 + 共享上下文累积」。**

```
Layer 1: Researcher → context_parts.append(研究成果)
    ↓ 共享前序成果
Layer 2: Planner → context_parts.append(行程规划)
    ↓ 共享前序成果
Layer 3: Budget + Foodie + Safety（并行）
    ↓ 每个 Agent 收到 base_request + "━━━ 前序 Agent 的工作成果 ━━━" + shared_context
```

**共享机制**：每完成一个 Agent，把输出追加到 `context_parts` 列表。下一个 Agent 的 user message = base_request + 所有前序 Agent 成果拼接。这样 Budget 能看到 Researcher 的天气信息和 Planner 的行程安排。

**追问准备（这个设计的代价）**：全量字符串拼接会导致 **token 膨胀**——到 Layer 3 时上下文已经很长。
当前缓解手段是「传成果文本不传消息历史」，但没做摘要压缩，这是已知短板。

### ★★ P6. 首次生成和多轮补充的链路路由怎么区分？


### ★★★ P7. 记忆怎么设计？长短期？

**两层架构。**

```
┌─────────────────────────────────────────┐
│  短期记忆（会话级）                        │
│  SQLite conversations 表（按 plan_id 隔离）│
│  生命周期：单次规划周期                     │
│  多轮对话：超过 10 轮自动摘要               │
└──────────────┬──────────────────────────┘
               │ 规划完成后提取用户偏好
               ↓
┌─────────────────────────────────────────┐
│  长期记忆（跨会话级）                      │
│  FAISS 向量索引 + SQLite memories 表       │
│  生命周期：持久化，跨会话复用               │
└─────────────────────────────────────────┘
```

**长期记忆组件**

| 组件 | 技术 | 作用 |
|------|------|------|
| 向量索引 | FAISS IndexFlatIP | 语义检索，512 维 |
| Embedding | bge-small-zh-v1.5 | 中文语义编码 |
| 元数据存储 | SQLite memories 表 | 原始文本+类型+目的地+标签 |
| 关联方式 | embedding_id | FAISS 索引 ID 关联 SQLite 记录 |

**记忆类型**：`fact`（用户事实，如"不吃辣"）· `preference`（偏好）· `interaction`（交互摘要）

**核心流程**
1. **写入**：规划完成 → LLM 提取偏好 → 编码 → 写 FAISS + SQLite → 去重（相似度>0.85 合并）
2. **读取**：新请求 → 语义检索 top-5 → 格式化注入 Agent 上下文
3. **反馈注入**：历史评分≤3 的低分反馈注入 prompt，提醒避免类似问题

**实测数据**（这是「记忆到底有没有用」的证据）：12 条记忆 / 8 个查询，
Recall@1 **75%** / Recall@3 **87.5%** / MRR **0.812**；
字面基线（字符 2-gram Jaccard）37.5% / 50% / 0.507 → **MRR 相对基线 +60%**。
8 条里有 1 条未召回，`eval/report_memory.md` 里如实列出。

**诚实边界**：用的是**构造语料**不是真实用户数据，证明的是检索方法的相对优势，不是线上效果。

### ★★★ P8. 工具怎么设计？Fallback 链是什么？

**7 个工具 + 参数归一化 + 三级错误恢复。**

| 工具 | 功能 | 数据来源 |
|------|------|---------|
| `get_weather` | 实时天气 | Open-Meteo API |
| `get_exchange_rate` | 汇率换算 | Exchange Rate API |
| `search_knowledge` | 知识库检索 | FAISS+BM25 混合检索 |
| `search_attraction_context` | 景点详情+关系 | 知识图谱 |
| `optimize_route` | 路线优化 | 贪心最近邻+2-opt |
| `optimize_budget` | 预算优化 | PuLP 线性规划 |
| `web_search` | 网络搜索 | DuckDuckGo + Wikipedia |

**参数归一化（`_normalize_tool_args`）**：LLM 可能传错参数名，自动适配，减少无效调用。

**三级错误恢复（`_execute_tool_with_recovery`）**
1. 执行原工具 → 失败
2. 重试一次 → 仍失败
3. 尝试 Fallback 工具链：`search_knowledge`→`web_search`、`get_weather`→`web_search`、
   `get_exchange_rate`→`web_search`、`optimize_route`→`search_knowledge`、`optimize_budget`→`search_knowledge`
4. 全部失败 → 返回降级提示「暂无数据」

**成本预算**：`web_search` 全局限 2 次，超限自动改走本地 `search_knowledge`（「成本感知路由」）。

**实测**：本地工具成功率 **95%**（80 次调用），最弱 `search_attraction_context` **80%**（部分城市缺细分条目）。
容错注入 4 类故障救回 3 类 → 最终可用率 75%，**一次成功率仅 25%**——
区分这两个数字的价值在于：只看前者会掩盖工具本身的不稳定。

### ★★★ P10. 动态路由怎么实现？为什么要做？

**Router Agent 分析用户意图，动态决定调用哪些 Agent。**

**为什么做**：省时间（只要预算就不用跑 5 个）· 省 token · 更聚焦

**两层实现**
1. **LLM 路由**：输出 JSON `{"agents": ["researcher", "budget"]}`
2. **规则路由 Fallback**：LLM 不可用时按关键词（"预算/便宜"→budget、"美食/餐厅"→foodie、"安全"→safety，默认全调）

**安全兜底**：`researcher` 和 `safety` 强制包含——调研和安全信息不能省。
（Safety 尤其关键：它的 system prompt 禁止调 web_search，紧急电话必须来自知识库，防编造。）

**注意**：路由只在 `mode=multi` 生效；默认 `single` 跳过路由。

### ★★★ P11. 并行化是什么？为什么做？怎么实现？ `[已修正：stagger 值]`

**Layer 3 的 Budget + Foodie + Safety 并行执行；另有 sequential 模式做对照。**

**为什么并行**：降低延迟（三者之和 → 取最大值）· 三者互不依赖，都只读前两层成果

```python
with ThreadPoolExecutor(max_workers=min(4, len(layer))) as executor:
    futures = {executor.submit(_run_parallel, a, i): a for i, a in enumerate(layer)}
    for future in as_completed(futures):
        agent_result, content, trace = future.result()
```

**关键细节**
- 错峰 `time.sleep(idx * settings.parallel_stagger_sec)`
  > **[已修正]** 默认 **1.5s**（`config.py:45`），原题库写的 2s/3s 是旧值
- `as_completed` 谁先完成谁先回调
- 令牌桶限流器控制全局并发（max_rps=10, max_concurrent=5）
- **消融**：`mode=sequential` 用来量「并行省了多少墙钟时间、有没有掉质量」→ 实测 471s vs single 202s

## 三、知识库与检索（2题）

### ★★★ P14. 混合检索引擎怎么实现？

**FAISS 语义检索 + 查询期 Okapi BM25 + GPS 邻近扩展，加权融合。**

1. **知识切分**：`DESTINATIONS` 按类别切 chunk（基本信息/景点/餐厅/交通/预算/安全）
2. **FAISS 语义索引**：bge-small-zh-v1.5 编码，`IndexFlatIP`（归一化内积 = 余弦相似度）
3. **Okapi BM25（查询期打分，不是建索引时写死分）**
   - 倒排存原始 term frequency
   - 查询时：`idf * tf*(k1+1) / (tf + k1*(1-b+b*dl/avgdl))`，**k1=1.5，b=0.75**
   - 中文按字、英文按词分词
4. **混合检索**：`combined = 0.7 * semantic_normalized + 0.3 * bm25_normalized`
5. **关系扩展**：`search_with_context()` 把 nearby（含公里数）和 same_type 拼进结果

**为什么混合**：语义擅长同义（"寺庙"≈"神社"），BM25 擅长精确（"东京塔"）。可用 `hybrid=False` 做消融。

**关键细节**：两者量纲不同，BM25 分要**除以最大值归一化**后再加权。

**被追问「那检索不到会怎样？」** → 这是本项目最容易被打穿的点，直接接 **P25**：
kNN 检索天然没有「拒答」能力，库外查询会返回语义最接近、但完全不相关的 k 条。
我已定位并修掉离线兜底那一处，回归测试在 `tests/test_crew_enhanced.py`。

### ★★★ P15. 知识图谱在项目里什么作用？

**是「地理邻近图 + 类型边」，不是通用知识图谱；邻近用真实 GPS 算，不用列表相邻冒充。**

```python
景点名 → {
    destination: "东京",
    type: "寺庙",
    nearby: ["东京晴空塔", "秋叶原"],   # Haversine ≤ 2.5km
    nearby_km: [1.37, 2.44],           # 真实公里数
    same_type: ["明治神宫", ...],
    has_gps: True
}
```

**构建方式**：从 `ATTRACTION_COORDS` 取真实经纬度 → Haversine 距离 → 半径 2.5km 内按距离排序取 top 5；
`same_type` 来自知识库 `type` 字段。仍是 Python dict，不需要 NetworkX——关系简单，不搞图算法。

**用途**：查「浅草寺」时返回附近是 1.4km 的晴空塔，而不是列表里碰巧写在旁边的景点。Planner 做「顺路逛」更合理。

**边界（被问「是真知识图谱吗」时这么答）**：不假装是 Wikidata。它是检索结果的**关系扩展**，
核心存储仍是 FAISS+BM25。只有部分景点有坐标，`has_gps` 字段如实标注了缺失。

## 四、评测与踩坑（3题）

### ★★★ P16. 怎么评估 Agent 效果？

**多评委打分 + 关键词覆盖 + 消融对比；失败也写进报告。**

1. **3 个 LLM 评委**（`app/evaluation.py`）：completeness（5 板块覆盖）· practicality（可执行性）· structure（结构与长度）
2. **取中位数 ×10** 作为 0–100 分（比平均抗极端值）
3. **关键词覆盖**：天气/景点/预算/美食/安全五类关键词是否出现，防「分高但空洞」
4. **消融（核心）**：`python -m eval.eval_runner --cases N --ablation`，同一批用例跑 4 组配置

**用例池**：`EVAL_CASES` 有 **15 个**标注用例（T001–T015）。
> **[已修正/补充]** 2026-09-15 的完整消融**实际跑了 3 个**（T001 东京 / T002 巴黎 / T003 曼谷），
> sequential 组 n=2。说「15 个用例」时务必补一句「消融跑了 3 个」，否则被追问样本量会翻车。

**实测结论**

| 配置 | 样本 | 平均分 | σ | 耗时 | ~成本 |
|------|------|--------|---|------|-------|
| **single + 反思** | 3/3 | **80.0** | **±0.0** | **202s** | **$0.0097** |
| multi + 反思 | 3/3 | 76.7 | ±5.8 | 324s | $0.0275 |
| multi 无反思 | 3/3 | 76.7 | ±5.8 | 226s | $0.0349 |
| sequential + 反思 | 2/2 | 75.0 | ±7.1 | 471s | $0.0418 |

**怎么用结论**
- multi 明显高于 single → 默认 multi
- 分差小且 multi 更慢 → 默认 single（**这才是更强的工程叙事**）
- 不稳定 → 先修失败，不贴最好一次

**为什么评测要先 `--check-quota`**：429 时 pipeline 会静默走离线降级，
跑满一小时得到的全是 0 次 LLM 调用的样本，旧报告里「0 分却标 ok」就是这么来的。
评测器对**离线降级、评委解析失败、Agent 全失败**的 run 自动隔离，不计入平均分。

### ★★★ P17. 开发 Agent 踩过哪些坑？

**坑 1：LLM 传错工具参数名**
LLM 调 `search_knowledge` 时传了 `city` 而不是 `destination`。
→ **解法**：`_normalize_tool_args()` 参数归一化。

**坑 2：工具调用 429 限流**
Layer 3 三个 Agent 同时调 LLM，瞬间 3 个请求触发限流。
→ **解法**：令牌桶限流（10 RPS）+ 错峰启动 + 指数退避重试。
> **[已修正]** 错峰是 `time.sleep(idx * settings.parallel_stagger_sec)`，默认 **1.5s**，
> 原题库写的 `idx * 3` 是旧值。

**坑 3：Safety Agent 漏章节**
6 个章节只输出 4–5 个，常漏「应急处理流程」。
→ **解法**：反思 prompt 逐项检查 6 章节，不通过自动修正。

**坑 4：对话历史过长导致 token 爆炸**
→ **解法**：超 10 轮自动摘要，前 N-4 条压成 200 字 + 最近 4 条原文。

**坑 5：SSE 断线后用户丢失进度**
→ **解法**：SSE 事件持久化到 SQLite，`/{plan_id}/events?after_id=` 回放（token 事件不落库，量太大）。

**坑 6：LLM API 完全不可用**
→ **解法**：`_generate_fallback_plan()` 离线降级，只靠知识库+算法出基础攻略。

**坑 7：完整 multi 要等很久，用户以为卡死**
→ **解法**：骨架优先——先本地秒出 Day 列表和预算粗解，Agent 后台填充，`final` 整体替换。

**坑 8：模型把「工具调用文本」当最终方案吐出** ⭐ 最值得讲
Function Calling 下偶发：正文是 `<tool_call>` / JSON，评测分极低（曾**单 Agent 20 分**）。
→ **解法**：`_looks_like_tool_dump()` 识别伪正文；过短或伪正文则强制无工具重写。
**修复后同配置从 20 → 70+。**

**坑 9：跑批被 429 污染出无效报告**
旧报告出现「0 分却标 ok」。
→ **解法**：评测器加 `--check-quota`（429 直接退出码 2），并对失败 run 自动隔离。

**坑 10：检索静默失败 —— 查库外城市返回别国内容** ⭐ 最新、最值得讲（→ **P25** 展开）
查「梅州五华」，返回吉隆坡餐厅、孟买预算、布宜诺斯艾利斯景点。
**这不是幻觉**：内容全是真的，只是跟查询无关 —— 所以比幻觉更难发现。
→ **根因两层**：① kNN 检索天然没有「拒答」能力，永远返回 k 条；
② 离线兜底调 `search_knowledge` 时**漏传 `destination`**，归属过滤没生效。
→ **解法**：补传参数 + 空结果给明确提示 + 加回归测试（**不 mock 检索**，否则测不到）。
→ **修复后**：库外 →「知识库暂未覆盖」；库内（东京）→ 照常出 5 条，**无回归**。

**坑 11：联网搜索在国内是坏的 —— 而且慢失败** ⭐ 第二个真 bug（→ **P26** 展开）
`web_search` 依赖 DuckDuckGo / Brave / Wikipedia，国内实测 **28.3 秒 / 0 条**。
而它是 **4 个工具的兜底终点**，等于整条降级链末端是断的，每次还先交 28 秒「买路钱」。
→ **核心判断**：**一个 28 秒才返回失败的兜底，比没有兜底更糟。**
→ **解法**：主后端换**必应中国 RSS**（实测 0.4s / 中文 / 免密钥）+ 海外源超时压到 5s
+ **冷却短路**（连续失败 2 次 → 冷却 5 分钟直接跳过）+ 降级前先查后端是否可用。
→ **修复后**：**28.3s / 0 条 → 0.33s / 3 条中文结果**；后端全挂时 0.000s 返回。
→ ⚠️ **我自己改出来的次生 bug**：P25 修复里我写死「建议改用 web_search」，
在国内是条死路，LLM 照做又白等 28 秒。**教训：给模型的每句指引，都要先确认那条路真的通。**

### ★★ P18. 记忆模块怎么设计？（补充多轮多会话）

（主体与 P7 一致）**补充多会话处理：**

### ★★★ P20. SSE 流式输出怎么实现？

**后端线程 + Queue + FastAPI StreamingResponse，前端 fetch + ReadableStream 消费。**

```python
def run_crew(q: queue.Queue):
    plan_id = db.create_plan_pending(...)
    def on_step(agent_name, content, progress):
        event = {"type": "agent_done", ...}
        q.put(event)
        db.save_sse_event(plan_id, "agent_done", event)  # 持久化
    result = build_travel_crew(..., step_callback=on_step, ...)

def event_generator():
    q = queue.Queue()
    thread = threading.Thread(target=run_crew, args=(q,))
    thread.start()
    while True:
        event = q.get(timeout=300)
        if event is None: break
        yield f"data: {json.dumps(event)}\n\n"
    yield "data: [DONE]\n\n"

return StreamingResponse(event_generator(), media_type="text/event-stream")
```

**事件类型**: status / skeleton / thought / action / observation / token / agent_done / final / error

**断线重连**：thought/action/observation/final/skeleton 落 SQLite，
`GET /{plan_id}/events?after_id=` 回放。**token 不落库**（量太大）。

**为什么用 SSE 不用 WebSocket**
- SSE 单向（服务端推送），够用了
- 基于 HTTP，部署简单，浏览器自动重连
- 支持 `Cache-Control: no-cache` + `X-Accel-Buffering: no` 防 Nginx 缓冲

### ★★★ P21. 并发控制怎么设计？ `[已修正：stagger 值]`

**令牌桶限流 + 指数退避重试 + 错峰启动，三层并发控制。**

**第一层：令牌桶（RateLimiter）**
- `max_rps=10`：每秒最多 10 个请求
- `max_concurrent=5`：最多 5 个并发（信号量）
- 令牌按时间补充，获取不到就等待

**第二层：指数退避重试**
```python
delay = base_delay * (2 ** attempt)     # 1s, 2s, 4s
jitter = delay * 0.2 * (2*random() - 1) # ±20% 抖动
time.sleep(max(0.1, delay + jitter))
```
**为什么加抖动**：大量请求同时失败会同时重试，形成**重试风暴**（thundering herd），抖动把它们打散。

**第三层：错峰启动**
并行 Agent 用 `time.sleep(idx * settings.parallel_stagger_sec)` 错开，
> **[已修正]** 默认 **1.5s**（`config.py:45`），原题库写的 2s/3s 是旧值。

### ★★★ P24. 「多 Agent 质量没提升，那你要它干嘛？」（2026-09-16 新增，必背）

> **这题是 P3 的必然追问。** 你在 P3 说「我用数据否定了自己的多 Agent 架构」，
> 面试官下一句一定是这个。答不上来，P3 的加分全部作废；答好了，这是全场最高光的 30 秒。

#### 第一步：先纠正口径（不说这句就会把自己绕进去）

**数据没有说「multi 不如 single」。** 80.0 vs 76.7，分差 3.3，**但 σ=5.8，分差比波动还小**。
这叫「**未见显著差异**」，不叫「single 更好」。

更关键的是——**`single` 快不是因为它更强，是因为它干的活少**：

| | LLM 调用次数 | 耗时 |
|---|---|---|
| multi（5 个 Agent） | **16.7 次** | 324s |
| single（1 个 `planner_all`） | **6.3 次** | 202s |

`single` 就是 1 个 Agent 拿全部 5 个工具、8 轮一把梭（`crew.py:1098` / `agents.py:141`）。
**少干活当然更快。拿 single 的耗时去证明"多 Agent 没用"是逻辑错误。**

#### 第二步：给出正确对照组（这是本题的答案）

要证明并行有没有用，得拿**同样 5 个 Agent** 互相比：

| 配置 | 墙钟 | 质量 |
|------|------|------|
| `sequential`（5 Agent 严格串行） | **471s** | 75.0 |
| `multi`（5 Agent，L3 并行） | **324s** | 76.7 |

**同样的 Agent 数、同样开反思，只把 L3 的 Budget/Foodie/Safety 并行掉，
省了 147 秒（1.45×），质量没有掉。** 这是这个项目里多 Agent 架构**唯一被数据直接证明**的价值。

#### 第三步：四条理由，各自标注证据强度

| 理由 | 强度 | 怎么讲 |
|------|------|--------|
| **并行省墙钟** | ✅ **有硬数据** | sequential 471s → multi 324s，1.45×，质量不掉 |
| **上下文隔离** | ⚠️ 结构性，本次未验证 | single 要把 5 板块 + 全部工具返回塞进 1 个 context；任务越长越吃亏，3 case 短行程测不出来 |
| **失败隔离** | ✅ 结构性 | 一个 Agent 挂了，其余 4 个照常出内容；single 一把梭只能整体重来 |
| **可独立替换** | ✅ 结构性 | 改预算只需重跑 Budget Agent（内部是 PuLP 线性规划），single 只能整体重跑 |

> **加分细节**：后三条标注成"结构性理由，本次消融未验证"，不要吹成已证实。
> 主动区分「我有数据的」和「我有理由相信的」，这是工程师和调库侠的分界线。

**代价也要说**：多 2.8 倍 token（16.7 vs 6.3 次调用）。多出来的调用买到的是模块化和并行，**不是质量**。

#### 第四步：30 秒标准答法（背这个）

> 多 Agent 在这个项目里的价值不是分数，是工程属性——同等质量下并行省 1.45 倍墙钟、
> 上下文隔离、失败可局部重试、模块可独立替换。质量上我没测出差异（分差比波动还小），
> 所以默认档选了更便宜的 single，把 multi 留成可选的深挖档。
> **这个结论是我跑消融跑出来的，不是抄来的。**

#### 追问：「既然没提升，为什么不删掉 multi？」（三层答法）

> 三个理由。
> **第一**，n=3 只够说「没观测到差异」，不够说「没有差异」，样本量不足以让我砍掉它。
> **第二**，三档可切换的抽象（动态路由、分层调度、并行执行器）本身是工程量，
> 也是我得出这个结论的实验设施。
> **第三**，上下文隔离的收益理论上随任务变长而放大，3 case 的短行程测不出来，
> 这是我下一步要补的实验。**如果 n=10 复测 multi 依然没有质量差异，我会把它正式降级为实验档。**

#### 分寸提醒

- ❌ 绝不能说「single 质量更好」——分差小于 σ，一说就被问穿
- ❌ 不能说「并行省 1.6 倍」——1.6× 是 single vs multi（活不一样多）；并行省的是 **1.45×**（sequential vs multi）
- ✅ 可以说「质量相当 + 成本更优 + 零波动 → 所以选 single」，这个完全站得住
- ✅ 最后那句「我会把它降级为实验档」很加分——说明你的结论是可被新数据推翻的

### ★★★ P25. 「你遇到过什么 bug？怎么定位的？」（2026-09-16 新增，必背）

**这是本项目唯一一个「我自己发现、自己定位、自己修、还留了回归测试」的真 bug，
比任何八股都值钱。** 完整档案：`docs/缺陷记录_检索静默失败.md`

#### 现象

查「梅州五华」，标题是《梅州五华 3日旅行攻略（离线版）》，正文却是吉隆坡餐厅、
孟买预算、布宜诺斯艾利斯景点。同一份输出里，路线 / 预算 / 天气三段**反而正确报错**
（未找到景点数据 / 无法生成预算 / 未找到城市坐标）。

#### 定性（这一句最关键）

> **不是幻觉，是检索的 out-of-domain 无拒答。**
> 幻觉是模型编造；这次每条内容**都是真的**，只是跟查询完全无关。
> 正因为它没有假事实，评测的事实一致性检查**抓不到它** —— 比幻觉更危险。

#### 定位过程（讲这个才像真做过）

1. 先跑复现脚本 `scripts/probe_retrieval.py`，确认知识库 28 个目的地里**没有梅州**
2. 对比两组查询的 top-5 归属：
   - 查「东京」→ **5/5 命中东京**，最高分 **0.6779**
   - 查「梅州五华」→ **0/5 命中**，分散在 3 个国家，最高分 **0.5603**
3. 读码定位到两层根因

#### 根因（两层，缺一不可）

| 层 | 问题 |
|---|---|
| 检索层 | `search_knowledge()` 用 FAISS `IndexFlatIP` 做 kNN，**天然没有「都不像」这个输出**；整个函数没有相关性阈值或归属校验 |
| 调用层 | `_generate_fallback_plan()` 调检索时**漏传 `destination`**，那道归属过滤压根没生效 |

**影响面**：不只是离线兜底。在线路径 `_execute_tool()` 里 `destination` 是**可选**参数，
大模型漏传时照样踩坑 —— 所以本质是**检索层缺「拒答」能力**，兜底函数只是第一个暴露点。

#### 我试过但放弃的方案（这段最加分）

第一反应是加个分数阈值，跑了数据发现**行不通**：
不相关最高分 **0.56**，相关最高分 **0.68**，**只差 0.12**。
阈值卡 0.60 在这两个样本上勉强能分，但样本量不足以标定，固定阈值必然误伤。

→ 改用**确定性判据**：目的地归属 / 覆盖校验。**不需要标定，稳。**

> 「我试过、失败了、换方案」比「我直接做对了」更像真做过项目的人。

#### 修复与验证

- **A 档（离线兜底）**：补传 `destination=destination`；空结果时输出「知识库暂未覆盖「XX」」（原来会**静默跳过**这一节）
- **B 档（治本，三件事）**：
  1. 检索入口加 `is_destination_covered()` 覆盖校验 —— 库外城市**直接跳过向量/BM25 检索**返回空
     （**刻意保留**用户上传文档的通道，否则会误伤已有功能）
  2. `_normalize_tool_args()` 给 `search_knowledge` 补 `destination` 兜底 —— 挡住「LLM 漏传」
  3. 文案区分 `未覆盖`（建议换城市/走 web_search）与 `没查到`；schema 里 `destination` 改**必填**
- 验证：库外 → 返回空 ✅；库内（东京）→ 仍正常出 5 条 ✅ **无回归**；不传 destination → 兼容 ✅
- 回归测试：`TestFallbackPlan::test_fallback_plan_out_of_domain_has_no_foreign_cities`
  + `TestOutOfDomainRetrieval`（6 个用例）。**都故意不 mock 检索** —— mock 掉就测不到这个 bug
- 全量测试 **261 passed**

#### 30 秒标准答法（背这个）

> 我在项目里发现过一个检索的静默失败：查一个知识库里没有的城市，系统不会说"没有"，
> 而是返回语义最接近的几条 —— 查梅州五华，返回的是吉隆坡餐厅和阿根廷景点。
> 内容全是真的，所以比幻觉更难发现。
> 定位下来是两层：kNN 检索天然没有拒答能力，加上离线兜底那次调用漏传了目的地过滤参数。
> 修的时候我先试了加分数阈值，跑数据发现不行 —— 相关和不相关的最高分只差 0.12，
> 阈值标定不住，所以改成目的地归属校验这种不需要标定的判据。
> 修完补了回归测试，并且特意不 mock 检索，否则测不到这个 bug。

#### 追问预案

| 追问 | 答法 |
|---|---|
| 这算幻觉吗？ | 不算。幻觉是编造，这是检索失败。内容为真但与查询无关，业界叫 out-of-domain 无拒答。 |
| 为什么不早发现？ | 输出长得像正常的，每条都经得起查。只有算法段（路线/预算/天气）诚实报错，形成反差才暴露。 |
| 分数阈值为什么放弃了？ | 0.56 vs 0.68 只差 0.12，样本不足以标定，固定阈值会误伤。 |
| 修完怎么验证？ | 复现脚本跑库内/库外各一组：库外返回空且提示未覆盖，库内照常出 5 条，确认无回归。 |
| 在线路径也修了吗？ | **修了**。B 档三件事：检索入口加覆盖校验（库外直接跳过向量检索）、参数兜底（漏传自动补本次规划的目的地）、schema 改必填。全量 261 passed。 |

#### 分寸提醒

- ❌ 不要说「全部完成」——A、B 两档都修了，但**检索相关评测数字还没重跑**（要 LLM 配额）
- ✅ 说「**A、B 两档都已修并验证，全量 261 个测试通过；评测数字待重跑**」
- ❌ 不要说这是幻觉 —— 说错暴露概念不清
- ✅ 强调「我跑了数据才放弃阈值方案」—— 这是区分真做和背答案的分水岭

### ★★★ P26. 「你遇到过什么 bug？」——第二个：联网搜索在国内是坏的（2026-09-16 新增，必背）

> **这题的价值和 P25 不同。** P25 证明「你会用数据定位问题」；
> P26 证明「你考虑过部署环境，并且**敢承认自己改错过**」。
> 后者在面试里稀缺得多——绝大多数候选人只会讲自己怎么修对的。

#### 现象（一句话）

联网搜索 `web_search` 依赖 DuckDuckGo / Brave / Wikipedia 等海外引擎，
**国内网络全部超时**，一份资料都拿不到。

#### 量化（关键：不是「感觉不行」，是实测数据）

> 清掉代理环境变量，模拟用户真实网络，10 秒硬超时：

| 后端 | 耗时 | 结果 |
|---|---|---|
| DuckDuckGo | 20.7s | 0 条（operation timed out） |
| Wikipedia | 9.8s | 0 条（handshake timed out） |
| **`web_search` 合计** | **28.3s** | **0 条** |

引擎轮换实测 `startpage` → `html.duckduckgo` → `search.brave`，**全部握手超时**。
**带代理对照同样是 28.3s / 0 条** → 不能靠代理救。

#### 为什么这比「功能缺失」严重（本题的核心判断）

> `web_search` 是 **4 个工具的兜底终点**：
> `search_knowledge` / `search_attraction_context` / `get_weather` / `get_exchange_rate`。
> 等于整条降级链的末端是断的，而且**每次走兜底都要先交 28 秒「买路钱」**。

**一句话记住**：

> **一个 28 秒才返回失败的兜底，比没有兜底更糟——它既救不了请求，又把流水线的时间预算占满了。**

这就把问题从「换个搜索引擎」升级成了「**慢失败 vs 快失败**」的工程问题。

#### 定位过程

1. 先写探针量化，**不猜**：清代理 → 打 `_ddg_search` / `_wiki_search` / `web_search`，记录耗时
2. 发现是超时不是报错 → 说明是**网络层不通**，不是解析逻辑坏了
3. 逐个试国内候选后端（同样无代理实测）：

| 候选 | 结果 | 结论 |
|---|---|---|
| **必应中国 RSS** `cn.bing.com/search?format=rss` | **200 / 0.4s / 中文** | **可直接用，免密钥** |
| Tavily API | 401 / 0.8s | 域名可达，有 key 即可用 |
| Serper API | 403 / 4.2s | 域名可达 |
| Brave 搜索 API | ConnectTimeout | 不可用 |

4. 抽检必应返回质量：查「梅州五华 旅游」→ 梅州市政府官网、梅州旅游攻略、梅州十大景点
   → **顺手把 P25 那个「查不到城市就只能编吉隆坡」的死循环也填了**

#### 修复（四步）

| # | 改动 |
|---|---|
| 1 | 主后端换**必应中国 RSS**，DDG / Wikipedia 降为海外备用（注册表可插拔） |
| 2 | 海外源显式短超时 **5 秒**（原为库默认 20s+） |
| 3 | **冷却短路**：后端连续失败 2 次 → 冷却 5 分钟，期间直接跳过 |
| 4 | `crew.py`：降级前先查后端是否可用；区分「搜了没结果」和「根本连不上」 |
| 5 | **接入国内官方 API**（智谱 / 百度 / 博查）：填 key 自动启用并排最前 |

> ⚠️ **第 5 步必须讲，否则会被打穿**：必应 RSS 是**未公开接口**，
> 只能算临时方案。官方 API 才是正式方案（有 SLA / 合规 / 账单）。
> 两家我**都实测过**，代码里是**两层并存**：
> 官方 API 优先（配 key 才启用）、RSS 兜底（保证零配置能跑）。
> **只讲「我换了必应」而不提官方 API，等于把临时手段说成正式方案。**

#### 我改出来的次生 bug（★ 这题的真正杀手锏）

> **P25 的修复里，我写的提示语是「建议改用 web_search 联网查询」。**
> 在国内这是**一条死路**——LLM 很听话，真去调了，于是又白等 28 秒。
>
> 后来改成按可用性动态生成：联网通就说能查，不通就直说不通。
> **教训：给模型的每一句指引，都要先确认那条路真的通。**

被问「你自己改出过 bug 吗」时，**主动说这个**，然后接这句总结——
这比任何「我很细心」都有说服力。

#### 验证

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单次调用 | 28.3s / 0 条 | **0.33s / 3 条中文结果**（约 85 倍） |
| 后端全挂时 | 等满 28.3s | **0.000s** 立即返回 |
| 全量测试 | 257 passed / 59.2s | **261 passed / 21.7s** |

> 测试套件快了 37 秒，因为测试里也会真实调 `web_search`——顺带证明了这个改动影响面有多大。

#### 30 秒答法

> 「我实测发现联网搜索在国内是 28 秒超时返回 0 条，而它是 4 个工具的兜底终点，
> 等于整条降级链末端是断的。我先量化了各候选后端，发现必应中国 0.4 秒可用、免密钥，
> 就把它提为主后端；然后加了冷却短路——后端连续失败两次就进冷却期直接跳过。
> **核心判断是：一个 28 秒才返回的兜底，比没有兜底更糟。**」

#### 追问预案

| 追问 | 答法 |
|---|---|
| 为什么不干脆只换国内引擎？ | 换引擎解决「搜不到」，冷却短路解决「搜不到时别拖垮流水线」。必应 RSS 是未公开接口，**一定会坏**——我要的是它**坏得体面**。两者是叠加不是二选一。 |
| 你自己改出过 bug 吗？ | **有**。第一版写死「建议改用 web_search」，在国内是死路，LLM 照做又白等 28 秒。**给模型的每句指引都要先确认那条路真的通。** |
| 0.4 秒是真的吗？怎么测的？ | 清代理环境变量模拟用户网络，httpx 直接打，记录状态码和耗时；对照组 DDG 和中文维基都超时，排除是我网络的问题。 |
| 必应 RSS 合规吗？ | ⚠️ **主动承认风险 + 给出正式方案**：RSS 是必应公开输出格式，但属**未公开接口**，只能算临时方案。国内三家官方 API（智谱 / 百度 / 博查）我**都实测过**：域名可达、0.2~0.3s、最便宜 ¥0.01/次，**代码也接好了，填个 key 就自动切过去**。保留 RSS 是作免密钥兜底，保证 clone 下来零配置能跑。 |
| 为什么不做成自动轮询多家 API？ | 不做。官方 API 有账单，静默轮询会让人搞不清钱花在哪家。只取第一个配了 key 的 provider。**涉及花钱的东西，显式比智能更重要。** |
| 接了官方 API，冷却短路还有用吗？ | 更有用。官方 API 也会限流、欠费、key 过期。短路保护的是**调用它的那一层**，跟后端是官方还是抓页面无关。 |
| 失败为什么不缓存？ | 缓存只存成功结果（防止把瞬时故障固化成永久故障，这是对的），副作用是每次失败都实打实重等。所以**不能靠缓存解决，要靠冷却短路**。 |

#### 分寸提醒

- ✅ 说「**已修并验证，0.33 秒出结果，全量 261 测试通过**」
- ✅ 主动说「必应 RSS 是未公开接口，生产要换官方 API」——**这是加分不是减分**
- ❌ 不要说「联网搜索做好了」—— 保住了**能用**，没做到**合规**，两者要分开说
- ❌ 不要只讲功能，一定要讲**「慢失败比失败更糟」这个判断** —— 这才是本题的得分点

# Part 4 · 补充八股 S1–S14（原题库没覆盖，但很常考）

> 这 14 题是 B1–B21 之外的缺口。按命中率排序，前 6 题命中率最高。

### ★★★ S1. RAG 是什么？为什么能减少幻觉？

**背**：检索 + 生成。解决三件事：**知识过期**（训练截止）、**私有数据**（模型没见过）、**幻觉**（答案有出处）。
流程：切片 → 向量化 → 存向量库 → 查询召回 top-k → 拼进 prompt → 生成。

**追问：RAG 一定会减少幻觉吗？**
→ **不一定**。检索到不相关内容反而会误导模型（distractor 问题）。
所以要做重排、相似度阈值过滤、引用标注。**这是区分「背过」和「做过」的分水岭。**

---

### ★★★ S2. 稠密检索 vs 稀疏检索，为什么混合？

| | 稠密（向量/语义） | 稀疏（BM25/TF-IDF） |
|---|------------------|-------------------|
| 优势 | 懂同义改写、泛化好 | 精确匹配强、可解释、零训练 |
| 劣势 | **专有名词/精确匹配差**（"浅草寺"可能召回成别的寺庙） | 不懂语义 |

**追问：BM25 比 TF-IDF 好在哪？**
→ 加了 **TF 饱和**（词频到一定程度不再线性加分，k1 控制）和 **文档长度归一**（长文档不占便宜，b 控制）。

**本项目**：`alpha=0.7` 语义 + `beta=0.3` BM25，k1=1.5 / b=0.75。BM25 除以最大值归一化后融合。

---

### ★★★ S3. chunk 怎么切？

- **固定长度 + overlap**：通用，简单
- **按语义/标题切**：结构化文档更好（本项目按类别切：基本信息/景点/餐厅/交通/预算/安全）
- **small-to-big**：检索用小 chunk，喂给模型时用大上下文，兼顾精度与完整

**坑**：切太碎丢上下文，切太大引入噪声。中文还要考虑按字还是按词。

---

### ★★★ S4. 召回后要重排（Rerank）吗？

要。向量召回是**近似**的，top-k 里混着噪声。
两阶段：快速召回（向量+BM25，top 50）→ **cross-encoder 重排**（top 5）。

**本项目没做 rerank** —— 这是最常被问到的短板。
**标准答法**：「目前是 0.7/0.3 加权融合，没有独立的 rerank 阶段。
下一步会接 bge-reranker，用 Recall@5 和消融平均分来验证收益。」
→ **主动承认 + 给出验证路径，比含糊带过强一百倍。**

---

### ★★ S5. 向量库怎么选？

- **FAISS**：库内嵌、单机、快，适合 <百万级、无分布式需求（本项目）
- **Milvus / Qdrant**：分布式、持久化、有元数据过滤
- **pgvector**：已有 Postgres 就顺手用，省一个组件

---

### ★★ S6. Embedding 模型怎么选？

中文场景：`bge-small-zh`（快，本项目，512 维）、`bge-m3`（多语言+稀疏稠密一体）、`text2vec`。
选型看：维度（存储/速度）、最大长度、领域是否微调过、是否支持**不对称检索**（query/doc 分开编码）。

---

### ★★★ S7. 上下文窗口怎么管理？

滑窗 / **摘要压缩** / 工具结果裁剪 / 结构化压缩。
**本项目**：多轮 >10 条时 LLM 摘要（保留最近 4 条原文）；工具结果只取前 300 字符；
Agent 间传成果文本不传消息历史。
**已知短板**：Layer 3 的上下文是全量拼接，没做压缩。

---

### ★★★ S8. Agent 成本怎么控制？

- **模型分级**：简单分类/路由用小调用（本项目路由 `temperature=0.1, max_tokens=200`）
- **缓存**：工具结果 TTL 缓存（命中率 47.5%）
- **预算**：贵工具限次（`MAX_WEB_SEARCH_CALLS=2`，超限降级本地）
- **早停**：`max_tool_rounds=3`
- **裁剪**：工具返回只取前 N 条

---

### ★★★ S9. 自我反思（Reflection）真的有用吗？

**诚实答**：学术界有 Refexion / Self-Refine，但**工业界收益不稳定**。
我的消融：开关反思得分完全一致（76.7，三个 case 逐个相同），关掉快 30%。
n=3 证据不强，但足以说明**没有可观测提升**。
反思在项目里的真实定位是**结构兜底**（防 Safety 漏章节），不是提分手段。

> ⚠️ 这题是陷阱：很多人会背「反思提升质量 20%」。
> 说出「我测了，没效果」——**这种诚实非常加分**。

---

### ★★ S10. 什么是 MCP？

Model Context Protocol：Anthropic 提出的**工具/数据源接入标准**。
解决 M×N 集成问题：M 个应用 × N 个数据源各自写适配 → 统一成 M+N。

**追问：和 Function Calling 什么关系？**
→ **不同层**。FC 是「模型调函数的格式」，MCP 是「工具发现和供给的协议」。两者互补，不冲突。

---

### ★ S11. 什么是 A2A？

Agent-to-Agent 协议（Google），解决**跨框架、跨组织的 Agent 互操作**——
用 Agent Card 描述能力 + 定义任务生命周期。
现状：早期，生产用的少。面试提一句说明你在跟进行业动态。

---

### ★★★ S12. Agent 有哪些安全风险？

- **Prompt Injection**：工具返回的内容里藏指令 → 隔离工具结果、权限分级、输出过滤
- **越权工具调用**：危险操作（删数据、付款）要人确认或白名单
- **数据泄露**：上下文里带了别的用户数据（多租户尤其致命）

**本项目的例子**：Safety Agent 的 system prompt **明确禁止调 web_search**，
紧急电话必须来自知识库——这是防「编造紧急联系方式」的安全设计，可以当例子讲。

---

### ★★ S13. 什么时候该微调而不是改 prompt？

Prompt/RAG 解决**知识**问题；微调解决**格式稳定性、风格、领域分布**问题。
顺序：先 prompt → 再 RAG → 再 few-shot → 最后才微调（成本高、迭代慢）。
**坑**：用微调「记住知识」是错的，知识该走 RAG。

---

### ★★★ S14. Agent 延迟怎么优化？

**先改体感，再改真实延迟**（这是产品思维）：
1. **体感**：骨架/流式/乐观渲染 —— 本项目把首屏可读从 3 分钟压到 **803ms**
2. **并行化**：无依赖的 Agent 并行（sequential 471s vs parallel）
3. **模型分级**：路由用小调用
4. **缓存**：工具 TTL 缓存
5. **裁剪**：上下文、工具返回
6. **早停**：轮次上限、关反思（快 30%）

# Part 5 · 手撕算法（Agent 岗也考）

| 题目 | 要点 | 出处 |
|------|------|------|
| LRU 缓存（带 TTL 更好） | 哈希表 + 双向链表，O(1) | 缓存设计必考 |
| **令牌桶限流** | 令牌按时间补充 + 信号量控并发 | 本项目 `concurrency.py` |
| Top-K | 堆 O(n log k) / 快排 partition O(n) | 检索召回本质 |
| 单调栈（B19） | 删重复字符字典序最小 | 已在上文 |
| 爬楼梯（B21） | DP + 滚动变量 | 已在上文 |
| **Haversine + 贪心 TSP** | 球面距离 + 最近邻 + 2-opt | 本项目真实代码 |
| 多线程 | ThreadPoolExecutor + Future + 异常传播 | 并行 Agent 层 |

**手撕 ReAct 循环**（10 分钟伪代码，很可能考）：
```python
def react(agent, user_msg, max_rounds=3):
    messages = [{"role":"system","content":agent.system},
                {"role":"user","content":user_msg}]
    for _ in range(max_rounds):
        msg = llm(messages, tools=TOOLS)
        if not msg.tool_calls:            # 无工具调用 → 最终答案
            return msg.content
        messages.append(msg)
        for tc in msg.tool_calls:         # 执行工具，结果回传
            result = execute(tc.name, json.loads(tc.arguments))
            messages.append({"role":"tool","tool_call_id":tc.id,"content":result})
    return force_final(messages)          # 轮次耗尽，强制收束
```

# Part 6 · 口诀速记 + 现场技巧

## 6.1 八股口诀

- **工具四层保障**：schema 约束 → 结构化输出 → 提示词约束 → ReAct 反馈
- **参数五步**：默认值兜底 → 尽力解析 → 保守假设 → 报告提示 → 多轮补全
- **输出控制五层**：schema 强约束 → 后处理归一化 → 提示词规则 → 后处理校验 → 自我反思
- **容错四道**：工具级 try/except → Agent 级兜底 → 编排级降级 → API 级错误返回
- **Badcase 归因**：缺失走补、错误走修
- **回归三防**：评测集回归检测、分维度指标监控、A/B 对比
- **优化九方向**：Prompt、结构化输出、工具工程、记忆增强、RAG、流程、容错、评测驱动、反馈闭环
- **工作流 vs Agent**：工作流管外层（确定性）、Agent 管内层（灵活性）
- **Function Calling**：定义→推理→解析→执行→回传→再推理→循环
- **降级四态**：ok / ok_retry / ok_fallback / failed（**只看最终可用率会掩盖不稳定**）

## 6.2 项目口诀

- **一句话**：手写 FC 多 Agent，**用消融证明多 Agent 不划算，默认改单 Agent**
- **三条结论**：质量打平（σ>分差）· 反思无收益（快 30%）· 并行价值在延迟
- **骨架优先**：本地秒出（803ms）→ Agent 填充 → final 整体替换
- **三种模式**：single（默认）/ multi（深度档）/ sequential（消融）
- **多 Agent 的理由**：不是分数，是工程属性——并行省 1.45× 墙钟 / 上下文隔离 / 失败隔离 / 可独立替换
- **对照组别搞反**：证明并行有用是 **sequential 471s vs multi 324s**，不是 single 202s vs multi 324s
- **single 快的原因**：只有 1 个 Agent、6.3 次调用（multi 16.7 次），**活少了不是变强了**
- **为什么留着 multi**：n=3 不够判死刑 · 三档抽象本身是工程量 · 上下文隔离待长任务验证
- **真 bug 一（P25）**：查库外城市返回别国内容 —— **不是幻觉，是检索无拒答**；0/5 命中、跨 3 国
- **阈值为什么不行**：不相关 0.56 vs 相关 0.68，**只差 0.12** → 改用「目的地归属」确定性判据
- **别把测试写废**：回归测试**不能 mock 检索**，mock 掉就测不到这个 bug
- **真 bug 二（P26）**：联网搜索国内 28.3s / 0 条，**还是 4 个工具的兜底终点**
- **慢失败比没有兜底更糟**：既救不了请求，又占满流水线时间预算 → **换引擎 + 加冷却短路**
- **冷却短路**：后端连续失败 2 次 → 冷却 5 分钟直接跳过（必应 RSS 是未公开接口，一定会坏）
- **我改出的次生 bug（P26，最诚实的一题）**：写死「建议改用 web_search」，而它在国内超时 ——
  **给模型的每句指引，先确认那条路真的通**
- **开源可跑**：github.com/mumu-abc/travel-planner（18 提交，能 clone 复现）
- **3 层执行**：L1 Researcher → L2 Planner → L3 Budget+Foodie+Safety 并行
- **两层记忆**：短期 conversations（plan_id 隔离）、长期 FAISS+SQLite memories
- **动态路由两路**：LLM 路由 → 关键词 fallback → 强制 researcher+safety
- **工具七把**：天气/汇率/知识库/景点详情/路线/预算/网络搜索（web_search 限 2 次）
- **三级错误恢复**：重试 → Fallback 链 → 降级提示 / 离线方案
- **伪正文拒收**：工具调用文本/过短 → 强制重写（20 → 70+ 分）
- **混合检索**：FAISS(0.7) + BM25 k1=1.5 b=0.75 (0.3) + GPS≤2.5km 邻近扩展
- **并发三层**：令牌桶 10RPS + 指数退避带抖动 + stagger 1.5s
- **SSE 九事件**：status / skeleton / thought / action / observation / token / agent_done / final / error
- **评测**：3 评委中位数×10 + 关键词覆盖 + 消融 + 失败隔离

## 6.3 现场五个「反杀」技巧

1. **被问「项目亮点」** → 不要说功能，说**决策**。
   「我用消融证明了自己的多 Agent 架构在这个场景不划算，默认改成了单 Agent。」
   比列十个功能强，而且是面试官没听过的答案。
   ⚠️ **说完这句必被追问**「那多 Agent 的理由是什么 / 为啥不删掉它」→ **背 P24**。

2. **被问「有什么不足」** → 说**真实的、你量化的**不足，再说下一步。
   「消融 n=3，分差小于波动，所以我不宣称 single 更好；下一步扩到 10 case 并加人工抽检。
   另外没做 rerank，这是已知短板。」

3. **答不上来时** → **不要编**。
   「这块我没实测过，但我的判断是 X，因为 Y，要确认的话我会做 Z 实验。」
   编答案被抓 = 直接挂；诚实 + 给出验证路径 = 加分。

4. **被问「你遇到过什么 bug / 最有成就感的事」** → 讲 **P25**，不要讲八股。
   按「现象 → 定性 → 数据 → 两层根因 → 试错 → 修复验证」的顺序讲，
   其中 **「我先试分数阈值，跑数据发现不行，才换成归属校验」是分水岭**——
   背答案的人讲不出这一步。
   ⚠️ 收尾必须说「**A、B 两档都已修并验证，全量 261 测试通过；评测数字待重跑**」，
   **别说含糊的「已修好」**。

5. **被问「你自己犯过什么错 / 改出过 bug 吗」** → 讲 **P26** 的次生 bug。
   > 「有。我修检索 bug 时给模型的提示语写死了『建议改用 web_search』，
   > 但联网搜索在国内是 28 秒超时——我指了条死路，LLM 照做又白等一轮。
   > 后来改成按后端可用性动态生成。**教训是：给模型的每句指引，都要先确认那条路真的通。**」
   ⚠️ **主动承认自己改错，在面试里是稀缺的**——绝大多数人只会讲自己怎么修对的。
   说完记得补一句「所以我后来加了冷却短路，让不可用的后端不会再被降级到」，
   把「认错」收成「有闭环」。
