# 缺陷记录：web_search 在国内网络下不可用

> 发现时间：2026-09
> 状态：**已修复并验证**（主后端换必应中国 + 快失败短路 + 降级链感知）
> 关联：本文件是 `缺陷记录_检索静默失败.md` 的续篇——上一篇修好了「库里没有时别乱答」，
> 本篇修的是「库里没有时该去联网，但联网是坏的」。

---

## 一、定性：不是「搜索质量差」，是「功能不可用 + 慢失败」

| | 说明 |
|---|---|
| 不是 | 搜到了不准的结果 |
| 是 | 一个都搜不到，而且要 **28.3 秒** 才知道搜不到 |

**为什么"慢失败"比"失败"更糟**：失败只是没拿到资料；慢失败除了没拿到资料，还把整条流水线的
时间预算占满了。而它是 4 个工具的兜底终点，等于每次走兜底都要先交 28 秒"买路钱"。

---

## 二、现象

用户报告：`ddgs` 依赖海外搜索引擎（DuckDuckGo / Brave / Wikipedia / Yahoo），
国内网络访问全部超时，`web_search` 基本不可用，只能回退本地知识库 `search_knowledge`。

---

## 三、实测数据

探针脚本（清掉代理环境变量，模拟国内无代理网络，10s 硬超时）：

```
DuckDuckGo     20.7s   0 条     error sending request ... operation timed out
Wikipedia       9.8s   0 条     _ssl.c:999: The handshake operation timed out
web_search     28.3s   0 条     ← 单次调用总耗时
```

引擎轮换实测：
`startpage.com` → `html.duckduckgo.com` → `search.brave.com`，**全部握手超时**。

带代理对照：同样是 28.3s / 0 条。说明**不能靠代理救**——`ddgs` 走的这条路本身就是断的。

### 国内候选后端实测（决定要不要换引擎）

| 后端 | 结果 | 耗时 | 结论 |
|---|---|---|---|
| **必应中国 RSS** `cn.bing.com/search?format=rss` | **HTTP 200，中文结果** | **0.4s** | **可直接用，免密钥** |
| Tavily API | 401 | 0.8s | 域名可达，有 key 即可用 |
| Serper API | 403 | 4.2s | 域名可达 |
| Brave 搜索 API | ConnectTimeout | 10s | 不可用 |
| 中文维基（对照） | ConnectTimeout | 10s | 不可用 |
| DuckDuckGo（对照） | ConnectTimeout | 10s | 不可用 |

必应 RSS 内容质量抽检（真实返回）：

- 查「东京 景点」→ 东京都百度百科、日本国家旅游局官网、GO TOKYO 官网
- 查「梅州五华 旅游」→ 梅州市百科、梅州市政府官网、梅州旅游攻略、梅州十大景点
- 查「巴黎 三日游 预算」→ 巴黎百科、知乎攻略、巴黎十大景点

→ **上一个缺陷里"梅州五华"查不到就只能编吉隆坡的死循环，换必应后直接不存在了。**

## 四、根因（三层）

| 层 | 问题 | 说明 |
|---|---|---|
| 1 | 后端选型没考虑部署地区 | 唯一的两个后端都是海外源，国内全不可达 |
| 2 | 慢失败 | 没有显式短超时，也没有"已知不可用就别再试"的机制 |
| 3 | 失败不缓存 | 工具缓存只缓存成功结果（这是对的），副作用是每次失败都实打实重等 28 秒，不会摊薄 |

### 放大器：它是 4 个工具的兜底终点

```python
_TOOL_FALLBACKS = {
    "search_knowledge":         ["web_search"],
    "search_attraction_context": ["search_knowledge", "web_search"],
    "get_weather":              ["web_search"],
    "get_exchange_rate":        ["web_search"],
    ...
}
```

### 我自己引入的次生问题（诚实记录）

上一篇修复里，`search_knowledge` 未覆盖目的地时的返回语写的是：

> "建议改用 web_search 联网查询"

在国内这句话是**错误的指引**——LLM 很听话，真的去调了，于是又白等 28 秒。
修一个 bug 时给模型指了条死路，这是本次最该记住的教训。

---

## 五、修复（四步）

| # | 改动 | 位置 |
|---|---|---|
| 1 | 主后端换成**必应中国 RSS**（0.4s、中文、免密钥），DDG/Wikipedia 降为海外备用 | `app/tools/web_search.py` |
| 2 | 海外源显式短超时 5 秒（原为库默认 20s+） | 同上 |
| 3 | **冷却短路**：某后端连续失败 2 次 → 冷却 5 分钟，期间直接跳过 | 同上 |
| 4 | 提示语改造 + 降级链感知后端可用性 | `app/crew.py` |

### 关键代码

```python
BACKEND_ORDER = ("bing", "duckduckgo", "wikipedia")

def _backend_usable(name):        # 冷却期判定
def _mark_backend_failure(name)   # 连续失败 2 次进冷却
def web_search_available()        # 供 crew.py 判断值不值得降级

def _call_backend(name, q, n):    # 按名字分发（便于测试 mock 替换）
```

`crew.py` 侧两处：

```python
# 1) 降级前先问一句：后端还活着吗
if fallback == "web_search" and not web_search_available():
    continue   # 明知道会失败的兜底就别去试

# 2) 区分「搜了没结果」和「根本连不上」
if not results:
    if not web_search_available():
        return {"success": False, "text": "联网搜索当前不可用（所有搜索后端均无响应）..."}
    return {"success": False, "text": "网络搜索未找到相关信息"}
```

`search_knowledge` 未覆盖时的提示语改成按可用性动态生成：

```python
hint = ("可尝试 web_search 联网查询" if web_search_available()
        else "联网搜索当前不可用")
```

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单次调用耗时 | 28.3s | **0.33s**（约 85 倍） |
| 单次调用结果数 | 0 条 | 3 条中文相关结果 |
| 后端全挂时 | 等满 28.3s | 0.000s 立即返回 |
| 全量测试 | 257 passed / 59.2s | **261 passed / 21.7s** |

## 七、为什么不设「绝对分数阈值」之类的兜底

（与上一篇同一条原则）联网搜索的"没结果"是**确定性**的——HTTP 超时就是超时，
不需要用相似度分数去猜。能用就用，不能用就说不能用，别拿一个调不准的阈值去判。

## 八、面试怎么讲

### 30 秒版

> "我实测发现联网搜索在国内是 28 秒超时返回 0 条，而它是 4 个工具的兜底终点，
> 等于整条降级链的末端是断的。我先量化了各个候选后端，发现必应中国 0.4 秒可用、
> 免密钥，就把它提为主后端；然后加了冷却短路——后端连续失败两次就进冷却期直接跳过。
> **核心判断是：一个 28 秒才返回的兜底，比没有兜底更糟，它既救不了请求又占满时间。**"

### 追问预案

**Q：为什么不直接换成国内搜索引擎就完了？**
> "换引擎解决的是'能不能搜到'，冷却短路解决的是'搜不到时别拖垮流水线'。
> 必应的 RSS 是未公开接口，会改版、会限流，所以它一定会坏——我要的是它**坏得体面**。
> 这两个是叠加关系，不是二选一。"

**Q：你自己改出来的 bug 有吗？**
> "有。我第一版修复里写了'建议改用 web_search'，结果在国内这是条死路，
> LLM 照做了又白等 28 秒。后来改成按可用性动态生成提示语。
> 教训是：**给模型的每一句指引，都要先确认那条路真的通。**"

**Q：0.4 秒是真实数据吗？怎么测的？**
> "清掉代理环境变量模拟用户网络，用 httpx 直接打，记录状态码和耗时。
> 对照组建了 DuckDuckGo 和中文维基，两者都超时，说明不是我网络的问题。"

**Q：必应 RSS 算不算爬虫？合规吗？**
> "这是我要标注的风险点：RSS 是必应公开输出的格式，但属于未公开接口。
> 生产环境应该换成必应官方 Search API 或有授权的数据源。
> **项目里我已经把后端做成了可插拔的 `BACKEND_ORDER`，换后端只改一处。**"

## 九、遗留

- 必应 RSS 为未公开接口，建议生产环境换官方 API（后端已可插拔）
- Tavily / Serper 域名可达，可作为「有 key 时优先」的可选后端，暂未接入
- `requirements.txt` 仍保留 `ddgs`，作为海外环境备用，未移除
- 评测数字（工具成功率等）尚未在改后重跑
