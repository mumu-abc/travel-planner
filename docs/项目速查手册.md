# travel-planner 速查手册（面试前 30 分钟过一遍）

> 目标：把「代码是 AI 写的、我记不住」变成「每个模块的决策我都说得出来」。
> 本手册只写**决策和可复述的结论**，不抄代码。代码细节用行号索引，需要时再定位。

---

## 0. 先搞清一件事：你为什么记不住

AI 生成的代码记不住，是因为**你没参与决策**。人脑记的是「我为什么选 A 不选 B」，不是「第 38 行写了什么」。

所以不要通读代码。正确的理解顺序是：

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1 | 跟一条请求走完全程 | 能画出数据流 |
| 2 | 对每个模块问：**它解决什么问题？去掉会怎样？** | 能说 trade-off |
| 3 | 动手破坏（关开关/改参数/断网） | 建立因果直觉 |
| 4 | 闭眼复述，卡住的地方回去看 | 发现真实盲区 |

**判断标准**：如果你能把每个模块用「因为 X，所以选 Y，代价是 Z」造句，就真的懂了。说不出「代价」= 没懂。

## 1. 一句话定位（开场白，必须背）

> 一个**手写 Function Calling** 的多 Agent 旅行规划系统（FastAPI）。核心不是「多 Agent」，而是**用消融实验量化多 Agent 到底值不值**——结论是质量打平但更慢更贵，所以默认档改成了单 Agent。

**这句话的杀伤力**：大部分候选人说「我做了个多 Agent 系统」，你说「我做了个多 Agent 系统，然后用数据证明它在该场景下不划算」。后者是工程师，前者是调库侠。

**项目真正在回答的两个问题**（README 开头原话）：
1. 体感：多 Agent 一跑几分钟，用户等不了 → 骨架优先压进 1 秒
2. 价值：多 Agent 相比单 Agent，质量/延迟/成本差多少 → 消融评测

## 2. 数据流：一次请求走完全程

对着这张图能讲出来 = 架构层面过关。

```
POST /api/plan/stream            app/routers/plan.py:89
  │
  ├─ 建 pending 记录（拿到 plan_id）         plan.py:94
  │
  ├─【骨架优先】不调 LLM，本地拼可读行程      plan.py:97 → app/skeleton.py:29
  │    知识库 + GPS 路线优化 + LP 预算
  │    推 SSE 事件 type=skeleton（P50 803ms）
  │    同时落库 db.save_sse_event ← 为断线重连
  │
  └─ build_travel_crew(...)                  app/crew.py:988
        │
        ├─ 注入用户历史偏好（user_preferences 表）   crew.py:1040
        ├─ 注入历史反馈闭环（低分→警告，高分→强化） crew.py:1058
        ├─ 注入语义记忆（FAISS 检索 top5）          crew.py:1083
        │
        ├─【路由】LLM 决定调哪几个 Agent            crew.py:909
        │     失败降级为关键词规则路由               crew.py:963
        │
        ├─【分层执行】split_layers()                app/agents.py:236
        │     L1 researcher → L2 planner → L3{budget,foodie,safety} 并行
        │     层内 ThreadPoolExecutor(4) + 错峰 1.5s 降 429
        │     前序 Agent 输出作为后序上下文拼接
        │
        └─【每个 Agent 内部】_run_agent_with_tools  crew.py:797
              Thought → Action(工具) → Observation → 循环(≤3轮)
                          │
                          └─ 工具失败：重试1次 → fallback链 → 降级文案
              → 输出校验（拒收工具调用伪文本）
              → 自我反思（PASS 则过，否则修正一次）
```

**关键细节（面试追问点）**：
- 骨架和 Agent 是**两条独立路径**，骨架不调 LLM，所以断网也能出东西
- SSE 事件**落 SQLite**，断线用 `GET /api/plan/{id}/events?after_id=` 回放；`token` 事件不落库（量太大）
- 上下文传递是**纯字符串拼接**（`━━━ 前序 Agent 的工作成果 ━━━`），不是共享内存

## 3. 模块地图（每个文件一句话）

| 文件 | 职责 | 面试怎么讲 |
|------|------|-----------|
| `app/agents.py` | 5 个 Agent 定义 + 反思 prompt + 分层 | Agent 定义拆出来是为了**可单测、可做消融** |
| `app/crew.py` | FC 引擎 · 路由 · 工具恢复 · 成本预算 | 整个项目的中枢，最该熟的文件 |
| `app/skeleton.py` | 本地骨架生成（无 LLM） | 体感优化的核心，803ms 的来源 |
| `app/concurrency.py` | 令牌桶 + 信号量 + 指数退避 | 10 RPS / 并发 5 / 退避带 ±20% 抖动 |
| `app/tools/knowledge_search.py` | FAISS + Okapi BM25 + GPS 图谱 | 混合检索，融合 0.7/0.3 |
| `app/tools/route_optimizer.py` | Haversine + 贪心最近邻 + 2-opt | 测试保证 2-opt 不差于贪心 |
| `app/tools/budget_optimizer.py` | PuLP 线性规划 | LP 不可用时回退比例分配 |
| `app/memory.py` | 偏好 + 向量记忆 | Recall@3 87.5%，MRR 比基线 +60% |
| `app/tool_metrics.py` | 工具成功率/降级率埋点 | **旁路记录，异常不影响主流程** |
| `app/tool_cache.py` | TTL 缓存，只缓存成功结果 | 失败不入库，避免固化瞬时故障 |
| `app/routers/plan.py` | SSE + 多轮 + 反馈 + 记忆 API | 多轮对话超 10 条做历史摘要 |
| `eval/eval_runner.py` | 消融评测 CLI | 有 `--check-quota`，429 时直接退出 |

## 4. 必须背的数字（说不出数字 = 项目没做过）

### 延迟
| 指标 | P50 | P95 |
|------|-----|-----|
| TTFB | 5ms | 16ms |
| **骨架可见** | **803ms** | **1080ms** |

### 消融（3 case × 4 配置，2026-09-15）
| 配置 | 样本 | 平均分 | σ | 耗时 | ~成本 |
|------|------|--------|---|------|-------|
| **single + 反思** | 3/3 | **80.0** | **±0.0** | **202s** | **$0.0097** |
| multi + 反思 | 3/3 | 76.7 | ±5.8 | 324s | $0.0275 |
| multi 无反思 | 3/3 | 76.7 | ±5.8 | 226s | $0.0349 |
| sequential + 反思 | 2/2 | 75.0 | ±7.1 | 471s | $0.0418 |

### 可靠性 / 检索
- 工具成功率 **95%**（80 次调用），最弱 `search_attraction_context` **80%**（照实报，不挑好看的）
- 容错注入 4 类故障，救回 3 类 → 最终可用率 75%，**一次成功率仅 25%**
- 缓存命中率 **47.5%**，第二轮省 38 次真实调用
- 记忆 Recall@1 **75%** / Recall@3 **87.5%** / MRR **0.812**，字面基线 37.5%/50%/0.507

**背法**：不要背表格，背**三条结论**（下一节）。

## 5. 三条结论（消融数据怎么讲，决定你是不是会思考的人）

1. **multi vs single 分差 −3.3，但 σ=5.8 → 分差小于波动**
   → 正确表述是「**质量未见显著差异**」，**不能说 single 更好**。
   但质量相当时 single 快 1.6×、省 2.8×、三次全 80 分零波动，所以默认选 single。
   **本质：用数据否定了自己设计的多 Agent 架构。**

2. **反思机制未观测到质量收益**
   → 开关反思得分完全一致（76.7，三个 case 逐个相同），关掉反而快 30%。
   n=3 存在巧合可能，但足以说明「没有可观测提升」。

3. **sequential 最差且最慢**（471s = single 的 2.3×）
   → **并行的价值在延迟，不在质量**。

> ⚠️ **这是本项目最大的加分项**。面试官见过一百个「多 Agent 很牛」的候选人，
> 没见过几个敢说「我测了，我这个场景不值得上多 Agent」的。

## 6. 设计决策与 trade-off（每个都要能说代价）

| 决策 | 为什么 | 代价 / 边界 |
|------|--------|------------|
| 默认 `single` 而非 `multi` | 消融：质量打平，快 1.6× 省 2.8× | 五板块齐全度不如 multi，故保留 multi 为深度档 |
| 骨架优先 | 3–6 分钟白屏不可接受 | 骨架是静态知识库，可能与最终方案有出入 |
| 手写 FC 不用 LangChain | 依赖轻、可控、无黑盒 | 自己实现工具循环/解析/容错，代码量大 |
| 混合检索 0.7/0.3 | 语义召回泛化 + BM25 保专有名词 | 权重是拍的，没做网格搜索 |
| 自建 BM25 | k1/b 可解释，中文按字切分 | 不如 jieba 分词准 |
| GPS 邻近图（≤2.5km） | 真距离，不是「列表相邻冒充图谱」 | 只有部分景点有坐标（`has_gps` 标了） |
| 工具 TTL 缓存 | 同城重复查询复用 | **只缓存成功结果**；天气 30min/汇率 1h/静态 24h |
| web_search 限次（2 次） | 贵工具不能想调就调 | 超预算自动降级本地知识库 |
| 反思可关 | 每次最多多 2 次 LLM 调用 | 消融显示无质量收益 → 演示可关 |
| 埋点旁路化 | 观测不能拖垮主流程 | 整体 try/except 兜底 |

## 8. 动手破坏清单（建立因果直觉最快的方式）

每个实验预期 5–10 分钟，**做完一个就多一个能讲的故事**：

| 实验 | 操作 | 预期看到 |
|------|------|---------|
| 关骨架 | `progressive=false` | 白屏等 3 分钟 → 体会骨架价值 |
| 切模式 | `mode=multi` / `sequential` | 日志打印层结构，观察耗时差异 |
| 关反思 | `enable_reflection=false` | 快约 30%，质量肉眼看不出差别 |
| 关缓存 | `ENABLE_TOOL_CACHE=false` | 同城二次查询重新调外部 API |
| 耗尽预算 | `MAX_WEB_SEARCH_CALLS=0` | 日志出现「预算耗尽，改走本地知识库」 |
| 断网 | 拔网线跑一次 | 工具全挂 → 走 fallback → 最终本地离线攻略 |
| 改融合权重 | alpha 0.7 → 1.0 | 专有名词召回变差（可讲消融） |
| 改邻近半径 | `2.5` → `10` | nearby 变多但「步行可达」失真 |

## 9. 已知边界（被问「有什么不足」时照实说）

这些都是 README 里**主动写出来的**，主动承认比被戳穿强一百倍：

- 消融 n=3（sequential n=2），**方向性结论**，分差 < 波动，不宣称 single 更好
- 工具成功率 95% **只覆盖本地工具**，天气/汇率/搜索走外部 API 未计入
- 缓存命中率 47.5% 来自合成负载，真实重复率取决于用户行为
- 记忆评测用**构造语料**，证明的是方法相对优势，不是线上效果
- 容错 4 类故障是**注入**的，不代表真实故障分布
- 单机 SQLite、无鉴权、无多租户 —— 是工程作品不是 SaaS
- 评委是 LLM-as-judge，有偏差，正式应加人工抽检
