# 消融对照说明（纯中文）

目的：用同一批评测用例，对比「多智能体」和「单智能体」谁的旅行方案更好、更慢，用数字说话，而不是靠感觉。

---

## 一、跑之前先准备

1. 已在 `.env` 里填好 `LLM_API_KEY`（能正常调用模型）。
2. 在项目根目录执行（和 `app`、`eval` 同级）。
3. 建议先用 **3 个用例**试跑，确认能出报告，再加大到 5～10 个。

本机若用 conda 环境，示例（路径按你的实际环境改）：

```powershell
cd C:\Users\钟利林\Desktop\travel-planner
D:\miniconda3\python.exe -m eval.eval_runner --cases 3 --ablation --output eval/report_ablation.md
```

只跑默认多智能体、不做对比时：

```powershell
D:\miniconda3\python.exe -m eval.eval_runner --cases 3 --output eval/report.md
```

想更快（关掉自我反思）：

```powershell
D:\miniconda3\python.exe -m eval.eval_runner --cases 3 --no-reflection --output eval/report_fast.md
```

## 二、消融会跑哪几组

`--ablation` 会在**同一批评测用例**上依次跑 4 组：

| 配置名 | 含义 | 想验证什么 |
|--------|------|------------|
| 多智能体 + 开反思 | 完整产品路径 | 主方案成绩 |
| 单智能体 + 开反思 | 一个模型写完五块 | 多智能体是否真的更好 |
| 严格串行 + 开反思 | 五个角色一个接一个，不并行 | 并行省时间还是掉质量 |
| 多智能体 + 关反思 | 去掉自我修正 | 反思值不值那些延迟 |

每组用**同样的用例、同样的模型、同一套三个评委**打分，避免「换个写法就换标准」。

---

## 三、报告里重点看哪几列

打开生成的 Markdown，先看 **「配置对比」** 表，再看明细。

### 1. 平均分（最重要）

- 三个评委分别打完整性、实用性、结构化（1～10 分），取中位数再乘 10，得到该用例百分制分。
- 对比：**「多智能体 + 开反思」** 对 **「单智能体 + 开反思」**。
- 记下分差，例如：多 76.7，单 62.0，分差 +14.7。

### 2. 关键词覆盖率

- 检查方案里有没有天气、景点、预算、美食、安全这几类信息。
- 覆盖率高，说明板块更全；用户「打开就能用」的可能性更大。

### 3. 平均耗时

- 多智能体通常更慢。
- 用「多花多少秒」换「多多少分」来判断值不值。

### 4. 成功数

- 若某组有失败（报错、空结果），先看失败原因，不要只比平均分。
- 失败多的组，分数不可信。

### 5. 明细表

- 看是不是「个别用例特别高把平均拉上去了」。
- 若只有曼谷 80 分、东京巴黎都很低，说明**不稳定**，不能直接写进简历。

## 四、分差多大才算「数」

没有官方阈值，下面按秋招项目可辩护的程度给参考（以 3～5 个用例为例）：

| 分差（多智能体 − 单智能体） | 怎么理解 | 建议说法 |
|---------------------------|----------|----------|
| 小于 +5 分 | 基本差不多 | 老实写：在本批评测上多智能体优势有限，单智能体可能够用 |
| 约 +5 ～ +12 分 | 有一定优势 | 可写「在本设置下更完整」，并注明用例数和模型 |
| 大于 +12 分，且每个用例都不崩 | 优势明显 | 可以较有底气写「多智能体更完整」 |
| 有的用例更高、有的更低 | 不稳定 | 先查失败原因和随机性，加大用例后再下结论 |

**额外要求（写简历前必须满足）：**

1. 用例数至少 3，更好是 5～10。  
2. 多智能体组**不能有系统性失败**。  
3. 关键词覆盖、平均长度不明显更差（避免「分高但空洞」或「很长但乱」）。  
4. 报告里保留失败记录，不要只贴最好的一次。

## 五、看完数字怎么决定「用户端要不要多智能体」

按下面三种情况对号入座：

### 情况 A：多智能体分数明显更高，覆盖也更全

- 用户端：默认用多智能体，保证方案完整。  
- 延迟痛点：用「关反思」或后续「先骨架、再填细节」缓解。  
- 简历：可以写「消融显示多智能体更完整」，并附分差。

### 情况 B：分数差不多，但多智能体慢很多

- 用户端：**默认单智能体更划算**；多智能体只做「深度模式」可选。  
- 简历：不要吹「多智能体更好」；改成「对比后发现单智能体性价比更高，因此产品默认 X」。  
- 这种结论反而更像会做取舍的工程师。

### 情况 C：多智能体更差或极不稳定

- 用户端：先修稳定性（工具失败、输出截断、路由漏板块），再谈架构。  
- 简历：不要写分数结论；只写工程能力（限流、降级、评测框架）。

## 六、建议的记录格式（跑完自己填）

```text
日期：2026-09-15（完整消融，T001 东京 / T002 巴黎 / T003 曼谷）
模型：mimo-v2.5-pro
用例数：3（sequential 因跑批中断为 2）
是否关反思：开/关两组均完成

single+反思：平均分 80.0  σ=0.0  平均耗时 202s  成功 3/3  ~$0.0097
multi+反思：  平均分 76.7  σ=5.8  平均耗时 324s  成功 3/3  ~$0.0275
multi 无反思：平均分 76.7  σ=5.8  平均耗时 226s  成功 3/3  ~$0.0349
sequential+反思：平均分 75.0  σ=7.1  平均耗时 471s  成功 2/2  ~$0.0418

分差（multi − single）：−3.3（分差 < σ，未见显著差异）
结论：B（质量未见显著差异；质量相当前提下 single 更快更省更稳）
一句话产品决策：默认 single；multi 保留为深度档。反思无可观测质量收益，关掉可省 30% 延迟。
```

## 七、常见问题

**问：一次要跑多久？**  
答：3 个用例 × 4 组配置，每组单次规划可能要数分钟，整体可能到半小时以上。请预留时间，不要中途改代码导致前后不可比。

**问：为什么不用更便宜的模型随便跑？**  
答：可以，但所有组必须**同一模型**。换模型等于换实验。

**问：分数是模型打的，会不会不靠谱？**  
答：会有偏差。所以还要看关键词覆盖、长度、成功数，并抽 1～2 份人工读一读是否真能用。

**问：用户完全不关心消融，为什么还要跑？**  
答：跑完你才知道该默认单智能体还是多智能体。**用户端该用哪个，由这份对比决定**，不是由「听起来高级」决定。

1. 确认 `.env` 有可用 Key。
